## 0. 符号表与重名提醒

> **约定**：本文出现的一切符号都在本节定义，后文不再重复解释（§0.6 列出的重名符号除外）。
> 反引号里的东西（如 `pos_r`、`green_mask`、`max_bands`）是**代码/JSON 字段名**，
> 字段级说明见 `docs/配置手册与数学原理.md`。
> `C1`～`C13`、`NRANGE`、`SYM`、`PLAN_WINDOW`、`WIN`、`MCC` 这类标签是
> **代码里的约束组编号**（写在 `ConstraintMeta.group` 里），不是数学符号。
>
> **变量命名**：模型变量名统一由 `greenwave/model/naming.py` 生成（前缀式：`gw_` 绿波 / `rw_` 红波 / `bnd_` 相位边界 / `win_` 路口窗口 / `bal_` 均衡组 / `soft_` 软约束），§0.3、§3.1 里的"代码里的名字"就是它。
>
> **单位约定**：时间一律是秒；`pos_r`、`δ`、`adjust` 是**周期比例**，乘 C 后得秒；
> 目标函数里每一项都用秒计价，所以带宽、margin 短缺、软约束违反量可以互相加减比较。

### 0.1 常量、集合与枚举

| 符号 | 含义 | 单位 / 类型 |
|---|---|---|
| `C` | 信号周期 | 秒（常数） |
| `κ` | 速度倍率格点（κ = 1 即按设计速度） | 无量纲常数 |
| `τ`（`τ_{i→j}`） | 路段 i→j 的行程时间 | 秒（常数） |
| `T_j` | 从需求链首到链上第 j 个位置的**累计**行程时间，`T_0 = 0`（下标 0 起，详见 §1.4） | 秒（常数） |
| `t` | **绝对时间**（概念上的时间轴；画时距图时的横轴） | 秒 |
| `T_max` | 全模型最大的累计行程时间，用来估 big-M 的量级 | 秒 |
| `N` | 路口总数（设计文档用 `N`，本文直接说"路口数"） | 整数 |
| `up` / `down` | 上行 / 下行方向 | 枚举 |
| `green` / `red` | 绿波 / 红波（带需求类型） | 枚举 |
| `I1, I2, …` | 路口 id（标识符，不是变量） | 字符串 |
| `I*_P*`、`GW_*`、`RW_*` | **id 命名习惯**，不是数学符号：`I4_P1` = I4 的第 1 个方案；`GW_up_full` = 上行跨全线绿波；`RW_down_6_5` = 下行 I6→I5 相邻对红波（Green/Red Wave） | 字符串 |

### 0.2 索引与下标

| 符号 | 含义 |
|---|---|
| `i` | 路口下标（i ∈ {I1, …, I6}） |
| `p` | 方案下标（路口 i 的第 p 个候选配时方案） |
| `d` | 方向下标（up / down） |
| `b` | **带需求**下标：一条需求 = 一条要在干线上一路通过的流 |
| `q` | 带槽下标：同一条需求最多开 q = 1…qmax 条时间上错开的带 |
| `j` | **需求链**（`band_demands[].nodes` 这个按行驶方向排好的路口清单）里的**位置下标**，0 起；`j = 0` 是链首，`j = len−1` 是链尾。第 j 个位置上的那个路口记作 `I_j`（= `b.nodes[j]`），详见 §1.4 |
| `y` | **相位边界下标**（一个方案在一个方向上的第几条边界），0 起。**代码里的变量名把边界下标写成第三键**（如 `bnd_delta[I2_P1,up,0]`），与上一行的「链位置 j」不是一回事——本文用 `y` 表示这个下标，详见 §0.6、§3.1 |
| `k` | 绿窗槽下标：该路口该方向的第 k 个**派生绿窗**（k = 1…最大窗口槽数） |
| `r` | 红窗槽下标（红波用：红窗 = 绿窗补集的第 r 段） |
| `g` | 上游绿窗槽下标（红波用，配 `rw_up_win[q,upslot]`） |
| `m` | 一个方向的**相位边界个数**（则 `green_mask` 有 m+1 段） |
| `c` | 软约束下标（`σ_c` = 第 c 条软约束的违反量） |
| `l` | Pareto 扫描的点序号（第 l 个 ε 点） |
| `v`（写作 `v1` / `v2`） | 建模版本标签：v1 = 窗口端点是独立变量；v2 = 端点是边界表达式（当前版本） |

### 0.3 决策变量

| 符号 | 代码里的名字 | 类型 / 界 | 含义 |
|---|---|---|---|
| `x_{i,p}` | `plan_on[{i},{p}]` | 0/1 | 路口 i 是否选方案 p |
| `δ_{p,d,y}` | `bnd_delta[p,d,y]`（第三键就是本文的 `y`） | **连续标量**；取值域 = 方案声明的 `adjust` 区间（**区间是它的上下界，δ 本身是一个值**） | 方案 p 在方向 d 的**第 y 条相位边界**的微调量，单位是**周期比例**（无量纲）：边界秒值 = `(pos_r + δ)·C` |
| `z_{p,d,y}` | `bnd_xdelta[p,d,y]` | 连续 | `z = x·δ` 的线性化辅助变量 |
| `φ_i` | `offset[{i}]` | 连续 [0, C]，锚点固定 0 | 路口 i 的周期起始偏置 |
| `u_{b,q}` | `gw_start[{b},{q}]` | 连续 **[0, C]（闭区间）** | 带槽 q 的**前缘到达「该需求链首」`b.nodes[0]` 的时刻**（带起点）。注意链首是**这条需求自己的第一个路口**，不一定是走廊的 I1（§1.4） |
| `β_{b,q}` | `gw_width[{b},{q}]` | 连续 [0, C] | 带槽 q 的宽度（= 能一路绿灯通过的时长） |
| `e_{b,q}` | `gw_on[{b},{q}]` | 0/1 | 带槽 q 是否存在 |
| `a_{b,q,j,k}` | `gw_win[{b},{q},{node},{slot}]` | 0/1 | 带槽 q 在链上第 j 个节点使用第 k 个绿窗槽 |
| `n_{b,q,j}` | `gw_cycle[{b},{q},{node}]` | 整数；**声明界**=该节点的并集区间（各窗口槽可行区间取并、含 0），选中窗口槽后由 `NRANGE` 行收紧到该槽的 `[n_lo, n_hi]` | 该节点用的是第几个**周期副本**的窗口 |
| `h_{i,d,k}` | `win_avail[...]` | 连续 [0,1]，由等式行 `h = Σ_p A·x_p` 定义（天然 0/1） | 绿窗槽 k 是否被选中方案提供 |
| `ag_{b,q,g}` | `rw_up_win[...]` | 0/1 | （红波）带槽 q 使用上游第 g 个绿窗槽 |
| `ar_{b,q,r,k}` | `rw_down_win[...]` | 0/1 | （红波）带槽 q 使用下游第 r 个红窗、第 k 个周期偏移 |
| `σ^{m,s}_{b,q,j,k}` / `σ^{m,e}_{b,q,j,k}` | `gw_margin_lo[...]` / `gw_margin_hi[...]` | 连续 ≥ 0 | 绿带在节点 j **用第 k 个窗口槽时**的左 / 右 margin 短缺 |
| `σ_c` | `soft_slack[...]` | 连续 ≥ 0 | 第 c 条软约束的违反量 |

### 0.6 重名提醒（同一个字母在本代码/文档里有多个含义）

读代码时最容易混的就是这几个，遇到时先看上下文：

| 字母 | 含义 1 | 含义 2 | 怎么区分 |
|---|---|---|---|
| `e` | 带存在性变量 `e_{b,q}` | 绿窗**终点** `e_{i,d,k}` / `ê` | 带下标 `(b,q)` 的是存在性；带 `(i,d,k)` 的是窗口终点 |
| `s` | 绿窗**起点** `s_{i,d,k}` / `ŝ` | margin 左侧短缺的上标 `σ^{m,s}` | 出现在 `σ` 的上标里就是"start 侧" |
| `n` | 整数回绕周期 `n_{b,q,j}`（变量） | —— （节点记号统一写成 `I_j`，不再用容易与 n 混的 `n_j`） | 看是否有下标 `(b,q,j)` |
| `m` | 相位边界个数（本文只讲这个） | 红波模型里"上游周期下标 `m`"（代码变量 `rw_up_cycle`，其专用紧 big-M 记作 `Mm`，§5.14.4） | 看是否出现在红波/`m_shift` 语境 |
| `k` | 绿窗槽号 `a_{b,q,j,k}` | 红波 `ar_{b,q,r,k}` 里的"下游周期偏移" | 看是绿波还是红波 |
| `z` | `z = x·δ` 线性化辅助变量 | 均衡组的 `z_g` | 带 `_g`（组）的是均衡组 |
| `j` | **需求链上的位置**（第 j 个节点 `I_j`；数学符号 `a_{b,q,j,k}`、`n_{b,q,j}`，代码名 `gw_win`、`gw_cycle`） | **相位边界下标**（第 j 条边界，`bnd_delta[p,d,y]`、PLAN_WINDOW 的 `b_y`） | 看它数的是「路口清单」还是「边界清单」；本文把边界下标写作 `y` |
| `T` | 累计行程时间 `T_j` | 绿掩码里的 `True`（写成 `[T, F]` 时是布尔） | 出现在 `[T, F]` 里就是布尔 |
| `C` | 周期 `C` | 约束组编号 `C1`…`C13`；"0/C" 里的 C 指周期接缝 | `C` 后跟数字 = 约束组 |
| `β` / `Β` | 小写 `β_{b,q}`：单条带的宽度 | 大写 `Β_b = Σ_q β_{b,q}`：该需求的**总**带宽 | 有没有求和 |
| `W` | 窗口宽度 `W = e − s` | C13 的 `W_g` / `Wr_{r,k}`：某类窗口的最大可能宽度 | 看下标是 (g) 还是 (r,k) |
| `M` | big-M | 方案边界个数 `m` 的大写形式（本文不用） | 看是不是"系数 × M"的语境；`M_hard` / `M_edge` / `Mm` 都是 big-M 的局部记法 |
| `h` | 绿窗槽可用性 `h_{i,d,k}` | —— （不是"小时"） | — |
| `A` | 指示量 `A_{i,p,d,k}` | —— （不是"案例 A"） | — |
| `L` | 路口损失 | —— | — |

### 0.7 与建模直接相关的配置字段（其余字段见配置手册）

| 字段 | 含义 |
|---|---|
| `boundaries` | 一个方向的相位边界位置列表（比例域，双周期在 (0, 0.5)） |
| `green_mask` | 逐段的布尔掩码（`true` = 这段是绿），长度 = 边界数 + 1 |
| `adjust` | 某个边界允许的微调区间（比例域）；不写 = 该边界固定 |
| `double_cycle` | 该方案是否双周期（相位图案在 (0, 0.5) 声明、复制两遍） |
| `min_phase_s` | 相邻相位边界之间至少隔多少秒 |
| `max_bands` | 这条需求最多开几条带槽（还要受 `qmax` 裁剪，见 §4.5） |
| `allow_window_sharing` | 是否允许同一条需求的多条带共用同一个绿窗（§7.4） |
| `weight` | 目标里这条需求带宽的权重（单位：秒 → 目标仍是秒） |
| `delta_min_s` / `coef` / `hard_min_s` | margin 的期望值 / 罚系数 / 硬下限（§5.10，仅绿波） |
| `red_boundary`（`free_s` / `coef` / `hard_max_s`） | 红波边界亲和：前 `free_s` 秒免费、超出按 `coef` 罚、可选硬上限（§11.6） |

## 1. 先建立物理图像

### 1.1 五个物理对象

| 物理对象 | 现实含义 | 数学身份 |
|---|---|---|
| **周期 C** | 信号灯循环一圈的秒数（如 140s） | 常数（某个格点下） |
| **相位方案** | 一个路口全天/某时段用的配时：几个相位、绿在哪几段 | 参数：`boundaries` + `green_mask` |
| **周期偏置 φ** | 这个路口的"周期从哪一刻开始" | 决策变量（连续） |
| **绿波带** | "一辆车以设计速度从第一个路口一路绿灯开过去"的时间走廊 | 决策变量：起点 `u` + 宽度 `β` |
| **路段行程时间 τ** | 上下游路口之间的行驶时间（距离 ÷ 设计速度） | 常数 |

再加两个"由上面派生出来"的东西：

| 派生对象 | 含义 |
|---|---|
| **绿窗（绿灯窗口）** | 某个路口、某个方向，在一个周期里车辆能通行的**连续时间区间** |
| **累计行程时间 T_j** | 从需求链首到链上第 j 个路口的累计行驶时间（链首 `T_0 = 0`） |

### 1.2 为什么必须是 MILP，而不是 LP

三个"要不要选"的逻辑，任何一种都足以把问题踢出线性规划：

1. **选哪个方案**：路口有 2~5 个候选配时方案，只能用一个 → `plan_on[i,p] ∈ {0,1}`；
2. **选哪个绿窗**：一个路口一个周期里可能有 2 段以上的绿灯，
   "这辆车走的是第 1 段还是第 2 段"是离散选择 → `a[b,q,j,k] ∈ {0,1}`；
3. **跨几个周期**：走廊长了以后，车辆到下游路口时已经是"下一个周期的绿灯"了，
   需要整数周期下标 → `gw_cycle[b,q,node] ∈ ℤ`。

除此之外的东西（φ、u、β、窗口端点）都还是连续的。所以这是一个
**混合整数线性规划**：连续变量负责"时间摆在哪、带宽多宽"，
0/1/整数变量负责"选哪一个"。

### 1.3 一条绿波带到底在优化什么

一句话：**存在一段时间区间 `[u, u+β]`，使得一辆车（或一列车队）在链上每一个
路口的到达时刻与离开时刻，都落在该路口被选中的那个绿窗里。**
`β` 就是"能一路绿灯通过的时长"，目标就是把它做大。

这里有个 MAXBAND 的经典技巧值得单独讲，因为它解释了为什么模型里**看不到 min**：

> 我们并没有为每个路口各设一个宽度再取最小。**全链共用同一个 `β`**，
> 然后要求 `[u, u+β]` 在**每个**路口都放得下。于是 `β` 自动被"最紧的那个路口"
> 卡住——最大化目标会把它顶到不能再大为止。
> 这就是"带宽由链上最紧的窗口决定，不需要额外写 min 函数"
> （`greenwave/model/builder.py:1047`）。

还有一个**必须一开始就知道**的结论（§8 会用实测数字讲透）：

> `φ` 是决策变量，除锚点外每个路口的窗口都能被 `φ` 自由挪动。
> 所以**单条带**的带宽上限就是"链上最窄的那个绿窗"，
> 协调本身在这里是免费的；**真正的难点来自多个需求共享同一组 φ**
> （上行带与下行带、多条带、多个 OD 之间互相争夺窗口的位置）。

### 1.4 什么是"需求链"（下标 j 到底在数什么）

一条带需求 `b` 在 JSON 里是"起点路口 + 方向 + 一串路口 + 权重"：

```json
{"id": "GW_up_full", "type": "green", "direction": "up",
 "nodes": ["I1", "I2", "I3", "I4", "I5", "I6"], "max_bands": 2, "weight": 5.0}
```

这串 `nodes` 就是**需求链**：这条带要求"车辆从第一个路口一路绿灯通过，
中途每个路口都要在绿灯里"，链上的顺序就是**车辆的行驶顺序**。
于是：

* `j` 是**链上的位置**（0 起）：`j = 0` 链首、`j = 1` 第二个路口……
  代码里到处用 `for j, node in enumerate(b.nodes)`；
* `I_j` 表示"第 j 个位置上的那个路口"（= `b.nodes[j]`）；
* `T_j` 是"从链首开到这个位置用的秒数"（`T_0 = 0`），递推式：

```
T_0 = 0 ,    T_j = T_{j−1} + τ(I_{j−1}, d)      τ(i, d) = 从路口 i 沿方向 d 出发那一段的行程时间
```

标准案例（C = 140s、κ = 1）的真实数字：

| 需求 | 链（nodes） | T_j（秒） | 每段行程 |
|---|---|---|---|
| `GW_up_full`（上行全线绿波） | I1 → I2 → I3 → I4 → I5 → I6 | 0, 13.3, 40.3, 52.8, 78.5, 91.1 | 13.3, 26.9, 12.5, 25.7, 12.7 |
| `RW_down_6_5`（下行相邻对红波） | I6 → I5 | 0, 11.2 | 11.2 |
| `RW_down_3_2` | I3 → I2 | 0, 23.3 | 23.3 |

读法：**上行的同一条走廊，下行的链是反过来的**（`I6 → I5 → … → I1`），
而且每段用的是**该方向的速度**（`speed_up_mps` / `speed_down_mps`），再除以 κ。
例如 I1→I2 是 200m、上行 15m/s → 13.3s；I6→I5 是 190m、下行 17m/s → 11.2s。

两条由校验强制的前提（`schema/validation.py:270`，规则 V4/V5）：

1. `nodes` 必须**沿该方向单调**（不能写反）；
2. `nodes` 必须**物理相邻、不能跳路口**——因为 `T_j` 是按链上相邻两项累加的，
   写 `[I1, I3]` 会漏掉 I2 那一段（校验会直接报错，不会静默算错）。

**三条容易搞混、但很关键的性质**：

1. **`u` 锚在"这条需求自己的链首"**，不一定是走廊的 I1。
   逐对窗口绿波里每个相邻对是独立需求，实测（C = 140s）它们的锚点各不相同：

   | 需求 | 方向 | 链（`nodes`） | `u` | `u + T_j`（各路口到达时刻） |
   |---|---|---|---|---|
   | `GW_up_I1_I2` | up | I1 → I2 | 140.00 | I1:140.0, I2:153.3 |
   | `GW_up_I2_I3` | up | **I2** → I3 | 140.00 | I2:140.0, I3:166.9 |
   | `GW_down_I6_I5` | down | **I6** → I5 | 80.88 | I6:80.9, I5:92.1 |
   | `GW_down_I3_I2` | down | **I3** → I2 | 0.00 | I3:0.0, I2:23.3 |

   `GW_up_I2_I3` 的 `u = 140` 是"到达 **I2** 的时刻"，与 I1 无关。
2. **同一条需求的所有带槽共享同一条链**：`q = 1, 2, …` 都从 `b.nodes[0]` 起算，
   槽与槽的区别只在 `u`（起点时刻）与 `β`（宽度），**不在起点路口**。
   "从中间路口开始"是**不同需求**之间的事。
3. **`u` 是"代表值"而不是"相位"**：`u` 取 `[0, C]` 闭区间（可以正好 = C），
   链首那个路口用第几个周期副本的窗口去接它由 `n` 决定（§8.1 的 `n = (1,0,1)`）。
   时距图就是按 `u % C + T_j` 定位每条带的（`report/diagram.py:158`）。

> 记号提醒：本文用 `I_j` 表示"链上第 j 个位置的路口"，
> 用 `n_{b,q,j}` 表示"整数回绕周期"。二者都与节点有关，
> 但一个是名词（路口）、一个是变量（周期副本编号），别混。

## 2. 时间轴与记号（最容易搞混的地方）

### 2.1 三个时间坐标

学生们最容易在这里翻车，所以先把三套坐标摆清楚：

| 坐标 | 定义 | 谁在用 |
|---|---|---|
| **绝对时间 t** | 从某个任意原点起算的秒数 | 概念上、画时距图时的横轴 |
| **干线的带起点 u** | 该带在**它自己需求的链首**（`b.nodes[0]`）的到达时刻；`[0,C]` 只是一个代表值域，具体用哪个周期副本的窗口由 `n` 对齐 | `u ∈ [0, C]` |
| **路口局部相位** | `t mod C` 落在 `[φ_i + s, φ_i + e]` 才算绿灯 | 窗口端点 `s, e` |

于是"带在链上第 j 个路口的到达时刻"就是：

```
到达(j) = u + T_j        （T_0 = 0，T 只与速度和距离有关）
离开(j) = u + T_j + β
```

**注意**：`u` 不随路口变，因为一辆车沿线开过去，它的"出发时刻"只有一个；
路口之间的差异全部体现在常数 `T_j` 以及各路口自己的 `φ_i` 上。

### 2.2 绿灯窗口长什么样

路口 i、方向 d 的第 k 个绿窗在**它自己的周期轴上**是 `[s_{i,d,k}, e_{i,d,k}]`。
换算到干线时间轴上，这个窗口在周期 `n` 的那一份是：

```
[ φ_i + s_{i,d,k} + n·C ,  φ_i + e_{i,d,k} + n·C ]
```

于是"带落在窗口里"就是：

```
u + T_j      ≥ φ_i + s_{i,d,k} + n·C
u + T_j + β  ≤ φ_i + e_{i,d,k} + n·C
```

这两行就是整个模型的心脏（C5）。`φ_i` 决定窗口在时间轴上的**位置**，
`s, e` 决定窗口的**形状**，`n` 决定用**哪一个周期的副本**。

### 2.3 为什么非要一个整数 n

因为 `u` 被限制在 `[0, C]`，而窗口是周期重复的。
先看本文的标准案例（6 路口、C = 140s）：全线累计行程只有 **91.1s ≈ 0.65 个周期**
（§1.4 的 T_j 表），此时 `n` 大多取 0 或 1。
走廊再长一点就不一样了：假设某条需求的累计行程是 200s（≈ 1.43 个周期），
车到链尾时已经比出发晚了 1.4 个周期；如果不给 `n`，
模型只能表达"第一个周期里的那个窗口"，这种长走廊的绿波根本写不出来。

准确地说：**`n` 挪的是"窗口的周期副本"，不是带**。
带的位置由 `u`（**该需求链首**的到达时刻，`u ∈ [0, C]`）唯一确定，
`n` 只是告诉模型"这个路口的窗口要从第几个周期副本里取"。
所以 `n` 在链首也可以是 1（例如 `u = C` 时窗口挪到下一个副本去接它），
每个节点的 `n` 各自独立——§8.1 的实测解里 `n = (1, 0, 1)` 就是这种情况。

`n` 的**可行范围**不是拍脑袋给的，而是用"区间必须相交"推出来的
（`builder.py:443` `_green_wrap_bounds_for_node`）：

```
n_hi = floor( (u_max + T_j − φ_min − s_min) / C )
n_lo = ceil ( (u_min + β_min + T_j − φ_max − e_max) / C )
```

推导：由 `u + T_j ≥ φ + s + nC` 得 `n ≤ (u + T_j − φ − s)/C`，
取各变量在各自界上最松的组合即 `n_hi`；由 `u + T_j + β ≤ φ + e + nC`
得 `n ≥ (u + T_j + β − φ − e)/C`，取最松组合即 `n_lo`。
若 `n_lo > n_hi`，说明**这个 (路口, 窗口槽) 组合下无论如何都不可能有整数 n**，
直接禁止选用它（`builder.py:1022`）——这是一条很有效的预剪枝。

> **工程上的坑（真实踩过）**：`n` 的区间是用 `φ` 的**上下界**推出来的，
> 所以 `φ` 必须在**建模之前**就定好。曾经试过"建完模型再钉 φ"，
> 结果 `n` 的区间还是老的，把最优解卡死了（`phi_fix` 参数因此存在，
> `builder.py:144`）。

### 2.4 锚点：φ 有一个自由度是假的

把所有路口的 `φ` 同时加一个常数 `Δ`，物理上**完全等价**（整个系统在时间上平移）。
这种"看起来不同、实际同一个解"的自由度叫 gauge 自由度。不处理它，
求解器会在一大堆等价解里打转。处理办法极简：**钉住走廊第一个路口（锚点，`corridor.intersections[0]`，标准案例里是 I1）的 φ = 0**
（`builder.py:199` `_build_offsets`）。

顺带解释一个后来做分解时的关键认知：
**正因为 φ 只是 gauge，跨路口的耦合看起来很强、其实很弱**——
这也是"逐对目标可以按路口拆开解"的物理基础。

## 3. 变量总表：逐个掰开

单位统一为**秒**（`δ` 与 `pos_r` 是比例，乘 C 后变秒；`β` 与目标里的罚项都是秒）。

### 3.1 方案层

| 变量 | 类型 | 界 | 含义 | 为什么需要它 |
|---|---|---|---|---|
| `plan_on[i,p]`（`x_{i,p}`） | 二进制 | [0,1] | 路口 i 选方案 p | 配时方案是离散菜单；单方案路口**不建**这个变量（直接代入，省 0/1 和 big-M 行，`builder.py:185`） |
| `bnd_delta[p,d,y]`（δ） | **连续标量** | 取值域 = 方案声明的 `adjust` 区间（区间是**界**，不是"δ 是个区间"） | 方案 p 方向 d 的**第 y 条相位边界**的微调量，单位是**周期比例**：边界秒值 = `(pos_r + δ)·C`。第三键就是边界下标，与「需求链位置 j」无关 | "允许把绿灯结束点往后挪一点"这种真实可调量 |
| `bnd_xdelta[p,d,y]`（z） | 连续标量 | `[min(0,lo), max(0,hi)]` | `z = x·δ` 的线性化替身 | 边界秒值是 `(pos_r + δ)·C`，而 δ 只在方案被选中时才该生效 → 乘积 `x·δ` 是双线性的，必须线性化 |

**双线性项 `z = x·δ` 的 McCormick 线性化**（`builder.py:245`）：

```
z ≤ hi·x            z ≥ lo·x
z ≤ δ − lo·(1−x)    z ≥ δ − hi·(1−x)
```

教学要点：`x ∈ {0,1}` 时这四条恰好逼出 `z = x·δ`
（x=0 → z=0；x=1 → z=δ）；`x` 连续时它给出的是凸包，是"最紧的线性放松"。
**常数端点也要乘 x**：如果方案在周期首尾有个**不含 δ 的常数端点**，
它同样要写成 `常数·x_p`，否则多方案时 Σ_p 会把常数重复计成"方案个数 × 常数"
（真实 bug：2 个方案时窗口端点被算成 2×，见 `greenwave/model/windows.py:67` 的注释）。

**⚠ `adjust` 是"界"而不是"δ 是个区间"**：δ 是**一个连续标量决策变量**，
`adjust: [lo, hi]` 只是它的上下界；而且这只是**盒子界**，别的约束可以把它压得更紧。
实测标准案例（C = 140s）：

| 方案 / 边界 | 声明 δ | 边界秒值的声明范围 | **实际可行范围** |
|---|---|---|---|
| `I1_P1`（没写 `adjust`） | —— | 恒为 70.0s | **不建 δ 变量** |
| `I2_P1` 边界 0 | [0, 0.20] | [56.0, 84.0]s | [56.0, 84.0]s（没被压） |
| `I3_P1` 边界 0 | [0, 0.20] | [42.0, 70.0]s | **[42.0, 49.0]s**（被红窗下限 `I3_up_red1_min_015C` 压住） |
| `I4_P1` 边界 0/1/2 | [0, 0.10] | [35,49] / [70,84] / [105,119]s | 与声明一致 |

三种情形：

* **不写 `adjust`** → 根本不建 δ，边界秒值是常数 `pos_r·C`（benchmark 里的"固定边界"就是这么做的）；
* **单方案 + 写了 `adjust`** → 建一个连续标量，直接进表达式 `pos_r·C + δ·C`；
* **多方案 + 写了 `adjust`** → **每个候选方案各一个 δ**，再加 `bz = x·δ`（McCormick 线性化），
  只有被选中方案的 δ 才生效。

另外两点：**双周期**复制出来的两份边界**共用同一个 δ**（所以一致性是结构性的，C11 是空实现）；
**同一路口 up/down 各写各的 `adjust` 时是两个独立 δ**，"上下行同时结束"要靠方案硬约束
（如 `I2_sync_up_down_end`）显式等起来，不是自动的。

**⚠ 两个 `j` 的分工**（读代码时最常混的一处）：

| | 数的是什么 | 取值域 | 出现在哪 |
|---|---|---|---|
| **边界下标 `j`**（本文写 `y`） | 一个方案在一个方向上的**第几条相位边界** | `0 … boundary_count(d)−1` | `bnd_delta[...]`、`bnd_xdelta[...]`、PLAN_WINDOW 的 `b_y`、方案约束里的 `boundary.index` |
| **链位置下标 `j`** | 一条需求的**第几个路口** | `0 … len(b.nodes)−1` | `gw_win[b,q,node,slot]`、`gw_cycle[b,q,node]`、`I_j`、`gw_margin_lo/hi[...]` |

两者都是 0 起，但**数的是完全不同的清单**，所以同一个数字含义不同。例如
`bnd_delta[I4_P1,up,1]` 是「`I4_P1` 上行第 2 条边界」，而 `gw_win[GW_up,2,I4,1]` 是
「`GW_up` 第 2 带槽在 **I4** 这个路口的指派」（`I4` 在链上是第 3 个位置）。

有个细节能帮你记住：**相位边界没有自己的名字，只能用序号**，所以边界下标出现在
变量名里（`bnd_delta[p,d,y]`）；而**路口有自己的 id**，所以链上位置的变量名写的是路口 id
（`gw_win[GW_up,2,I4,1]`、`gw_cycle[GW_up,2,I4]`），`j` 只是代码里的循环下标。

### 3.2 路口时间层

| 变量 | 类型 | 界 | 含义 |
|---|---|---|---|
| `offset[i]` | 连续 | `[0,C]`，锚点固定 0 | 路口 i 的周期起始偏置 |
| `win_avail[i,d,k]` | 连续（自动 0/1） | [0,1] | 有效窗口槽 k **是否被选中方案提供**。`h = Σ_p A_{i,p,d,k}·x_p`，`A=1` 表示方案 p 至少有 k 个派生窗口（`windows.py:130`） |

`h` 的妙处：它把"选中的方案有几个绿段"这件事**变成一个连续变量**，
从而下游约束（`a ≤ h`）全都保持线性。它声明为连续，但因为
`Σ_p x_p = 1`，取值天然落在 {0,1}。

### 3.3 绿波带层（每条需求 b、每个带槽 q）

| 变量 | 类型 | 界 | 含义 |
|---|---|---|---|
| `u[b,q]` | 连续 | `[0,C]` | 带在**该需求链首**（`b.nodes[0]`）的到达时刻（前缘） |
| `beta[b,q]` | 连续 | `[0,C]` | 带宽度 = 能一路绿灯通过的时长 |
| `e[b,q]` | 二进制 | {0,1} | 这条带槽**是否存在**（允许"少用几条带"） |
| `gw_win[b,q,node,slot]`（`a_{b,q,j,k}`） | 二进制 | {0,1} | 带 q 在**链上某路口**使用的**窗口槽**（键里写路口 id） |
| `gw_cycle[b,q,node]`（`n_{b,q,j}`） | 整数 | 声明界 = 该节点的并集区间（含 0）；选中窗口槽后由 `NRANGE` 收紧到 `[n_lo, n_hi]` | 带 q 在该节点用的是第几个周期副本 |

**关于 `e` 与 `a` 的分工**（初学者常问"为什么不干脆只留 a"）：

* `Σ_k a[b,q,j,k] = e[b,q]`：带存在 → 每个路口**恰好**挑一个窗口；
  带不存在 → 一个都不挑（C4）；
* `β ≤ C·e`：带不存在 → 宽度必须是 0（C6）；
* `e` 也让目标可以写成 `Σ_q β`（不存在的带自动贡献 0），
  而不需要写"只有 e=1 时才计入"的分段函数。

**关于 `a` 为什么按路口单独索引**（这是理解绿波最关键的三个点之一）：

> `a[b,q,j,k]` 的下标里有 `j`，意味着**同一条带在每个路口各自挑窗口**：
> 完全可以是"在 I1 走第 2 段绿、在 I2 走第 1 段绿、在 I3 走第 1 段绿"。
> 窗口槽号 k 是**结构顺序**（第 k 个绿段），不是"第 k 号物理相位"：
> 一个方案在第 1 个绿段，另一个方案的第 1 个绿段可能完全在别的位置。
> `n` 则负责把这些"各自挑的窗口"对齐到同一辆车的轨迹上。

**关于 `n` 的下标**：它只挂在 `(b,q,j)` 上、不挂在 k 上，
因为"用第几个周期副本"是**该路口该带**的统一偏移，窗口槽的选择已经由 `a` 表达。

### 3.4 放松量（见 §7）

| 变量 | 含义 |
|---|---|
| `gw_margin_lo` / `gw_margin_hi[b,q,node,slot]` | 绿带左右两侧**离窗口边界太近**的"短缺量"（margin 罚） |
| `soft_slack[约束名.pos/.neg]`（σ） | 一条**软约束**的违反量 |

## 4. 窗口是怎么"派生"出来的

这一节回答"窗口选择"的原理：候选窗口不是人手工指定的，而是**从配时方案里算出来的**。

### 4.1 把周期切成 m+1 段

一个方案的一个方向长这样（v2 plan-native 格式）：

```json
"up": { "boundaries": [0.25, 0.5, 0.75], "green_mask": [true, false, false, false] }
```

* `boundaries`：m = 3 个**相位边界**，比例域（单周期 (0,1)，双周期 (0,0.5)）；
* `green_mask`：m+1 = 4 个布尔，逐段说明"这一段是不是绿"；
* 于是周期的边界序列（含首尾）是 `[0, 0.25, 0.5, 0.75, 1]`，
  四段依次是：绿、红、红、红 → 绿窗 `[0, 0.25C]`。

代码：`expanded_edge_sources`（`schema/models.py:503`）把首尾常数端点与声明边界
统一编号成 edge 0..m+1；`expanded_mask`（`schema/models.py:507`）给出掩码。

### 4.2 极大绿段 = 派生窗口（不是任意子区间）

`_windows_from_ratios`（`schema/models.py:515`）把**连续为绿**的段合并成
**极大绿段**，每一段就是候选窗口槽 k = 1, 2, …：

```
mask = [T, F, T, T, F]   →  窗口槽 1 = 第1段, 窗口槽 2 = 第3~4段合并
```

**为什么必须是极大段？** 因为"窗口"是用来做包含约束的容器：
只要带宽放得下，车走在极大段里的哪一段都行，所以把极大段切成两半
只会制造对称的冗余变量。这条规则同时给出一个硬性校验：
**掩码的首尾不能同时为绿**，否则绿段跨越 0/C 首尾相接、
"极大段"会被切成两半（`schema/models.py:516` 直接报错并要求旋转方案）。

### 4.3 双周期：掩码复制两遍

`double_cycle=True` 表示这个路口一个**周期**里配时图案重复两遍，
边界比例声明在 `(0, 0.5)`。实现上（`schema/models.py:488`）先把整周期展开成：

```
0 → [b_0 … b_{m−1}] → 0.5（常数 seam）→ [b_0+0.5 … b_{m−1}+0.5] → 1
```

即 `expanded_mask = mask + mask`、边界复制一份加 0.5，并在半周期处补一个
**常数边界 0.5**（seam），最后按位置排序。于是派生窗口数量翻倍，
但**两份共用同一个 δ**——一致性是结构性的，不需要额外等式（C11 因此是空实现，
`builder.py:953`）。这就是为什么"双周期路口要 `max_bands=2` 才有意义"。

### 4.4 有效窗口：把"方案选择"折进窗口表达式

对路口 i、方向 d、窗口槽 k，定义**有效窗口**（`windows.py:102`）：

```
ŝ_{i,d,k} = Σ_p  x_p · s_{p,d,k}(δ_p)          ← 起点表达式
ê_{i,d,k} = Σ_p  x_p · e_{p,d,k}(δ_p)          ← 终点表达式（跨 0 的 +C 也乘 x_p）
h_{i,d,k} = Σ_p  A_{i,p,d,k} · x_p ,  A=1 ⇔ 方案 p 至少有 k 个派生窗口
```

三个要点：

1. **窗口端点不再是变量**，而是方案边界 δ 的**线性表达式**。这是 v2 相对
   v1（每个端点一个独立连续变量）的关键决策：省掉一批变量、省掉"端点 ↔ 边界"
   的一致性问题，但要求所有用到端点的地方都改写成表达式。
2. `h` 是"这个槽位有没有被选中方案提供"的门：
   `a[b,q,j,k] ≤ h[i,d,k]`，槽位不存在就不许选。
3. **槽位 k 是结构对应，不是位置对应**：I1 的槽 1 是 I1 的第 1 个绿段，
   I2 的槽 1 是 I2 的第 1 个绿段，两者在时间轴上的位置可能天差地别。
   真正把"位置"对齐的是 φ 与 n。
4. **槽位数量 K 是按"最胖的候选方案"预定的，没被用上的槽位会被钉死并松弛**
   （详见 §4.4.2）。


#### 4.4.1 `s/e` 和 `ŝ/ê` 差在哪（三层关系）

初学者最容易把这两个看成"同一个东西的两种写法"，其实它们处在**三层**上：

| 层 | 记号 | 是什么 | 谁在用 |
|---|---|---|---|
| ① 每方案·比例 | `s_{p,d,k}` / `e_{p,d,k}`（比例域常数） | `PlanSpec.derived_windows(d)` 给出的该方案第 k 个绿窗，如 `I1_A: (0.0, 0.5)`、`I1_B: (0.0, 0.05)` 与 `(0.4, 0.9)` | **预处理**：`qmax`、回绕整数 n 的可行区间、红窗兼容对 `(g,r,k)`、C13 的 `W_g/Wr`、端点上下界 |
| ② 每方案·激活后（秒） | `x_p·pos_r·C + C·z_p`（+ 跨 0 的 `x_p·C`） | `_plan_window_endpoint_expr` 生成的分项：**只有该方案被选中时才有效**，δ 通过 `z = x·δ` 进入 | 只是 ③ 的求和分项，不单独进约束 |
| ③ 有效窗口 | `ŝ_{i,d,k}` / `ê_{i,d,k}` | `Σ_p`（②）——**每个 (路口, 方向, 槽位) 只有一份**，是"选中方案折出来的那个窗口" | **所有约束与目标**：C5、C8、红窗构造、红带包含 |

实测（C = 100s，I1 两个方案：A 单段绿、B 两段绿；两者都在第 1 条边界上声明了 `adjust`）：

```
① I1_A: (0.0, 0.5) → [0, 50]s          I1_B: (0.0, 0.05) → [0, 5]s
                                              (0.4, 0.9)  → [40, 90]s
   K(I1, up) = max(1, 2) = 2

③ ŝ_{I1,up,1} = 0                                         ← 两个方案都从比例 0 起，退化成常数
   ê_{I1,up,1} = 50·x[I1_A] + 5·x[I1_B] + 100·z[I1_A] + 100·z[I1_B]
   ŝ_{I1,up,2} = 40·x[I1_B]                               ← 只有 B 提供第 2 段
   ê_{I1,up,2} = 90·x[I1_B]
   h₁ = x[I1_A] + x[I1_B] ≡ 1      h₂ = x[I1_B]           ← 槽位"在不在"（§4.4.2）
```

读法：

1. **粒度不同**：① 是**每方案一套**（A 一套、B 两套，各自从槽 1 编号）；③ 是**每路口每槽位一份**，
   数量 `K = max over 方案`。所以 `ŝ_{I1,up,2}` 只可能是 B 的贡献。
2. **是否含选择逻辑**：① 是常数；③ 是线性表达式，`Σ_p x_p·(…)`，未选中方案的项被 `x_p = 0` 抹掉；
   δ 通过 `z = x·δ` 只在被选中时生效（§3.1 的 McCormick）。
3. **退化**：单方案路口不建 `x`，此时 `ŝ = s·C`、`h ≡ 1`，**两者重合**；多方案时才分叉，
   甚至可能出现"端点退化成常数"（上面的 `ŝ_{I1,up,1} = 0`）或"只剩一个方案的项"。
4. **为什么必须分**：约束里**绝不能出现某个方案的裸端点**（`pos_r·C` 是常数）——
   那等于"不管选不选它都得满足"，多方案就没意义了。所以约束一律用 ③，
   而预处理阶段（还没建 `x`、只知道每个方案的形状）只能用 ①。
5. 另外别忘了 `ŝ/ê` 只给**端点**，`h` 给**存在性**；在 A 被选中的情形下
   `ŝ_{I1,up,2} = 0` 数值无意义，但 `h₂ = 0` 会把 `a[...,2]` 钉成 0、C5 全被 big-M 松弛，
   这个值**永远不会被读到**（§4.4.2）。

#### 4.4.2 槽位为什么"预定了很多"，没选中的会怎样

一个路口可能既有"单段绿"的候选方案，也有"两段绿"的候选方案。
于是模型按**最胖的那个方案**预定槽位：`K = max_p(方案 p 的派生绿窗数)`。
多出来的槽位不会凭空浪费，它们被一个**开关变量** `h` 管住：

```
h_{i,d,k} = Σ_p A_{i,p,d,k} · x_p        A = 1 ⇔ 方案 p 至少有 k 个绿窗
```

实测（I1 有两个候选方案：A = 单段绿 [0,50]，B = 两段绿 [0,5] + [40,90]，C = 100s）：

```
K(I1, up) = max(1, 2) = 2          # 两个槽位

WIN 行（h 的定义）：
  h[I1,up,1] − x[I1,I1_A] − x[I1,I1_B] = 0      →  两个方案都有第 1 段 ⇒ h₁ ≡ 1
  h[I1,up,2] − x[I1,I1_B]              = 0      →  只有 B 有第 2 段 ⇒ h₂ = x_B

a ≤ h 行：
  gw_win[GW_up,1,I1,2] − win_avail[I1,up,2] ≤ 0  →  没选 B 时这个指派必须为 0
```

因为 `Σ_p x_p = 1`，右边恰好是 0 或 1，所以 **`h` 天然是 0/1**——
它不是一个"松弛量"，而是一个**由等式行定义的开关**
（代码把它建成变量而不是直接写表达式，是为了让红窗能复用它的组合，
例如"跨 0/C 的红段可用 ⇔ h_r = 1 且 h_{r+1} = 0"，见 `windows.py:172-175`）。

**"没选中的槽位被松弛掉"这个理解是对的，机制是两步**：

1. `a[b,q,j,k] ≤ h[i,d,k]` → `h = 0` 时该槽位的指派变量被**钉成 0**；
2. C5 的包含式挂着 `M(1 − a)` → `a = 0` 时这些行**整体被 big-M 松弛**。

所以不存在的槽位不会产生任何有效约束。顺带一个实现细节：槽位 k 的端点表达式
`ŝ_k / ê_k` 在构造时**跳过**了"绿窗数 < k"的方案（`windows.py:121`），
因此当选中方案没有第 k 段绿时，这个表达式其实退化成常数、数值上没有意义——
但因为 `a ≡ 0`，引用它的 C5 全被松弛，**永远不会被读到**。

两个边界情况：

* **单方案路口**：`K` 就是该方案的绿窗数，且 `h` 的界直接给成 `[1,1]`
  （`windows.py:113`）——等式行仍会生成，但退化成 `h − 1 = 0` 的冗余行，
  预处理会直接消掉；
* **双周期路口**：绿窗数翻倍 → `K = 2`，这才是"双周期要 `max_bands=2`
  才有意义"的由来。

最后别把 `h` 的作用放大：它只管**存在性**。窗口的**位置与宽度**仍由
`x_p · 端点_p(δ_p)` 与 φ 决定——两个方案都"有第 1 个绿窗"，
但一个在 [0,50]、另一个在 [0,5]，这正是 `a ≤ h` 不够、C5 还必须引用 `ŝ/ê` 的原因。

### 4.5 带槽数量 qmax 的裁剪（"能开几条带"）

一条需求能开几条带（qmax）不是想要多少就要多少，`ctx.demand_max_bands`
（`preprocess/context.py:76`）取：

```
链上结构上限 chain_max = min over 节点 ( 该节点方向的最大绿段数 )
绿波:  allow_window_sharing ? max_bands : min(max_bands, chain_max)
红波:  max(1, max_bands or 3)      （前提：下游路口有绿窗）
```

教学解释：

* **chain_max 是"结构上限"**：如果某个路口一个周期只有 1 段绿，
  你就不可能开 2 条**时间上不重叠**的带穿过它（C7 的圆环分离不允许重叠）；
* **`allow_window_sharing=True` 时不再用 chain_max 封顶**：因为一个绿窗可以
  "分时复用"给多条时间不重叠的带（例如左转带和直行带错开），
  此时瓶颈节点的绿窗数量不再是带宽条数的上限；
* 单周期、每路口一段绿 → qmax = 1，模型里根本不建 `q=2` 的那套变量
  （这是"自适应的模型裁剪"，见设计文档 §4.8）。

## 5. 约束逐条推导

记法：绿波需求 b，链上第 j 个位置的路口 `I_j`（= `b.nodes[j]`），方向 `d_b`，累计行程 `T_j`（`T_0=0`），
大 M 见 §5.14。

### 5.1 C1 方案选择

```
Σ_p x[i,p] = 1                    ∀i        （builder.py:196）
```

"每个路口必须且只能选一个方案"。单方案路口不建 `x`，直接当成常数 1 代入。

### 5.2 C2 方案内硬约束（big-M 条件激活）

方案自带的约束（例如"上行绿灯结束点 ≤ 0.7C"、"上下行绿灯同时结束"）
只在**该方案被选中**时才必须成立（`builder.py:747`）：

```
sense 为 ≤  :  lhs + M·x ≤ rhs + M      即  lhs ≤ rhs + M(1−x)
sense 为 ≥  :  lhs − M·x ≥ rhs − M      即  lhs ≥ rhs − M(1−x)
sense 为 == :  上面两条同时加
```

* `x = 1` → 退化成原约束；
* `x = 0` → 右端放宽 M，约束自动成立（不起作用）。

M 的取法：按该约束里每个原子在**声明范围内**的最大可能量级估
（边界原子用 `(pos_r+adjust_ub)·C`，窗口时长用 `3C` 等），
再取 `max(估计总量, |rhs|) + 1`（`builder.py:380`）。
**绝不用 1e6 这种通用大 M**：会毁掉 LP 松弛质量、引发数值问题。

### 5.3 方案内软约束（C3）：不是"必须"，而是"尽量"

同一位置如果写成软约束（`soft.coef > 0`，`builder.py:763`），就变成：

```
lhs ≤ rhs + σ_c + M(1−x) ,   σ_c ≥ 0
```

`σ_c` 是"违反了多少秒"，然后按 `coef` 罚进目标（composite 或 intersection_loss，
由 `owner` 决定）。**硬约束 = 边界，软约束 = 有价格的边界**，
这是建模里最重要的取舍工具，详见 §7.2。

### 5.4 PLAN_WINDOW：相位自身的合法性

方案内部的相位必须有序且不太短（`builder.py:919`）：

```
b_0 ≥ min_phase                     （秒）
b_y − b_{y+1} ≤ −min_phase            （相邻边界至少隔 min_phase 秒；y 是边界下标）
b_{m−1} ≤ hi·C − min_phase            （hi = 0.5 双周期 / 1.0 单周期）
```

没有这一条，"绿窗"可以退化成 0 秒宽，模型会给出物理上做不到的解。

### 5.5 C4 绿带指派

```
Σ_k a[b,q,j,k] = e[b,q]                  ∀b,q,j     （builder.py:1102）
a[b,q,j,k] ≤ h[I_j, d_b, k]              ∀b,q,j,k   （builder.py:1112）
```

第一行：带存在 ⇔ 每个路口**恰好**挑一个窗口槽；
第二行：只能挑**被选中方案真正提供**的槽位。

教学要点（三个"为什么"）：

* 为什么是 `= e` 而不是 `≤ 1`？因为带宽 β 需要在每个路口都有容器，
  漏掉任何一站这条带就不成立；
* 为什么用 `h` 而不是直接对 `x` 写大 M？因为"方案 p 提供不提供第 k 个绿段"
  这个信息在**预处理**就知道（`A_{i,p,d,k}`），折进 `h` 之后，约束变成
  一对一线性的 `a ≤ h`，非常干净；
* 为什么窗口槽用**结构顺序**编号？因为不同方案的绿段位置不可比，
  只有"第几个绿段"这个顺序对所有方案都良定义。

### 5.6 C5 绿带包含约束（核心）

对每个 (q, j, k) 两条不等式（`builder.py:1131` / `builder.py:1140`）：

```
u + T_j          ≥ φ_{I_j} + ŝ_{I_j,k} + n_{b,q,j}·C − M(1 − a[b,q,j,k])
u + T_j + β      ≤ φ_{I_j} + ê_{I_j,k} + n_{b,q,j}·C + M(1 − a[b,q,j,k])
```

逐项翻译：

| 项 | 含义 |
|---|---|
| `u + T_j` | 这辆车到达第 j 个路口的时刻 |
| `u + T_j + β` | 队尾离开该路口的时刻 |
| `φ + ŝ + nC` | 该路口那个绿窗的起点（第 n 个周期副本） |
| `φ + ê + nC` | 该绿窗的终点 |
| `−M(1−a)` / `+M(1−a)` | "只有当你真的选了这个窗口，这两条才必须成立" |

**为什么这样就够了（不需要为每个路口定义带宽）**：见 §1.3，
全链共用 β，最紧的窗口自动卡住它。

**为什么 `n` 出现在两侧**：窗口整体平移 n 个周期，起点终点一起平移，
所以 n 同时出现在上下两条里——这也解释了 NRANGE 为什么用"两条不等式的
区间相交"来推 n 的可行范围。

### 5.7 NRANGE：n 的紧区间与"不可行槽位"剪枝

`builder.py:986` 把 §2.3 算出来的区间接进模型：

```
n ≤ n_hi + M(1−a)        n ≥ n_lo − M(1−a)         （选中该槽位时才收紧）
e = 0 → n = 0                                        （n ≤ hi·e, n ≥ lo·e）
n_lo > n_hi 的槽位  →  a ≡ 0                          （直接禁止）
```

这三条是**性能**关键：

* 把 n 的界从"全局最坏"收紧到"逐 (节点, 槽位)"，搜索空间小一个数量级；
* `a ≡ 0` 提前删掉物理上不可能的窗口选择，比让分支定界去发现便宜得多；
* `e=0 → n=0` 让不存在的带不会"占着" n 的界。

### 5.8 C6 存在性

```
β ≤ C·e                    （builder.py:1148）
```

`e=0` 时 β=0（不存在的带不贡献目标、也不占用圆环时间）；
`e=1` 时 β ≤ C（物理上带宽不可能超过一个周期，其实 C4/C5 已经更紧了）。

### 5.9 C7 多带：排序、圆环不重叠、窗口独占

同一条需求的多个带槽之间（`builder.py:1155`）：

```
u_q ≤ u_{q2}                                   （按起点编号，破对称）
u_q + β_q ≤ u_{q2}                             （q 在 q2 之前结束）
u_{q2} + β_{q2} ≤ u_q + C                      （q2 绕回 0 点后仍不压到 q）
（以上均带 M·e 项条件激活）
```

为什么这三条：两条带如果时间上重叠，它们其实可以被**合并成一条更宽的带**，
最大化目标不会偏好拆分，所以禁止重叠不丢最优解；反过来，
不禁止重叠就会让"同一条物理带被数两遍"，目标虚高。
第二条 + 第三条合起来表达的是**圆环上的不重叠**（时间轴是首尾相接的圆）。

**窗口独占**（默认，`builder.py:1180`）：

```
Σ_q a[b,q,j,k] ≤ 1     （同一条需求的多个带槽不能共用同一个绿窗）
```

这条是**轻度保守**的（设计文档 §4.7 有完整论证）：
若两条带在所有路口都共用同一窗口，它们可以合并，禁止无损失；
只有当它们**部分路口共用、部分路口不同**时，独占才会切掉真实最优。
因此 schema 留了 `allow_window_sharing` 开关：打开后不加这条独占行，
只保留始终存在的圆环分离（同需求内部仍然时间不重叠）。

> **别把它的作用说大**：关掉独占只是**放宽可行域**（同时把 `qmax` 的上限
> 从"链上最窄窗口数"放开到 `max_bands`），所以理论上不会更差；
> 但**能不能真拿到更优解取决于实例**。在标准案例的双周期配置上实测
> （4 种目标 × k=1/2、固定边界、20s 上限）：开关只把逐对绿波类目标的 `qmax`
> 从 1 提到 2，**8 个配置里 7 个目标值完全相同**
> （`GW_window_both` k=1 两者都是 420.9558、k=2 都是 478.9942；
> `RW_both_window`、`GW_up_global_RW_down` 也都一样），
> 剩下 1 个差 0.0002（且两侧都是 time_limit）；另有 1 例打开后从 optimal
> 变成 time_limit——因为约束与变量都变多了。

### 5.10 C8 绿带 margin：把"太贴边"变成钱

现实里带宽贴着绿灯边界不好（排队、清空时间），所以引入**margin**：
带宽起点距离窗口起点、终点距离窗口终点，各自希望至少有 `δ_min` 秒。

**硬下限**（`hard_min_s > 0` 时，`builder.py:1195`）：直接写成 C5 的加强版，
把 `u + T_j ≥ φ + s + nC` 换成 `u + T_j ≥ φ + s + nC + hard_min`。

**软短缺**（`delta_min_s > 0, coef > 0`，`builder.py:1230`）：

```
σ^s ≥ δ_min − (u + T_j − φ − ŝ − nC) − M(1−a)      （左侧不够的部分）
σ^e ≥ δ_min − (φ + ê + nC − u − T_j − β) − M(1−a) （右侧不够的部分）
σ ≥ 0
```

然后 composite 减去 `coef · Σσ`。教学要点：

* 这是"**软约束的最小化写法**"：`σ ≥ 短缺` 而不是 `σ = 短缺`，
  因为目标在最小化 σ，最优时会自动取等号；
* σ 是对**每一个 (q, j, k)** 建的，没被选中的窗口靠 `M(1−a)` 放松、σ 取 0；
* **报告里的 margin 损失不是直接读 σ**：σ 只是"模型认为的下界"，
  解码时用几何法重新算真实短缺（`report/solution.py:253`
  `_actual_margin_penalty`）——这是一个值得记住的工程习惯：
  **目标函数里的松弛变量值可以大于真实违反量，报告要重算**。

### 5.11 C10 用户全局约束

用户可以写"上行总带宽 ≥ 15s（硬）"、"上行总带宽尽量 ≥ 20s（软）"这类
跨需求的约束（`builder.py:1681`，代码里的 group 是 `USER_HARD` / `USER_SOFT`）。

**可用原子只有三种**：`offset`（φ）、`bandwidth`（`Β_b = Σ_q β`）、`const`。
`boundary` / `window_duration` / `red_duration` 是**方案作用域**的原子，
写进全局约束会被校验规则 **V7** 直接拒绝（`schema/validation.py:61`），
即使绕过校验，建模层也会抛
`GWModelError: boundary atom referenced outside a plan constraint`（`builder.py:284`）。
想写"某个绿灯至少要多长"这类要求，得写进**方案自己的** `hard_constraints` /
`soft_constraints`（C2/C3），或用作用域模板 `constraint_templates`。

硬约束直接加行，软约束走 `σ + coef·owner`。

### 5.12 C13：给红波补的有效不等式（顺带讲"怎么加强模型"）

红带的指派被因式分解成 `ag`（上游绿窗槽）与 `ar`（下游红窗实例）两组 0/1
（设计文档 §4.3，`builder.py:1270`）。因式分解后，`β` 与所选窗口宽度之间的
联系被 big-M 拉松了，于是补两条**有效不等式**（valid inequality，代码 group = `C13`）：

```
β ≤ Σ_g W_g · ag[q,g]            + C(1−e)     W_g = 所选上游绿窗的最大可能宽度
β ≤ Σ_{r,k} Wr_{r,k} · ar[q,r,k] + C(1−e)     Wr  = 所选下游红窗实例的最大可能宽度
```

（红带还有第三条 `β ≤ C·e`，但它是**存在性**约束、代码归在 `C9`，不算有效不等式。）

这两条**不改变可行整数解集合**（对每个整数解都成立），但显著收紧 LP 松弛——
这是"为了提高求解效率而额外加的数学"，在绿波里没有（绿波靠 NRANGE 与
对称破缺），在红波里必须有。

### 5.13 对称破缺：合法地删掉等价解

多带槽的模型有天然对称：把"槽 1"和"槽 2"换个名字还是同一个解。
`_add_band_slot_symmetry`（`builder.py:961`，仅在 stage-1 打开）加两条：

```
e_q ≥ e_{q+1}                （存在的带必须排在前面）
β_q ≥ w_min · e_q            （存在的带至少 w_min 宽，w_min 默认 1.0s）
```

第一条删掉空槽的排列对称；第二条删掉"e=1 但宽度为 0"的退化分支。
**注意**：第二条引入了"最小带宽"这个建模限制，
所以 `min_band_width_s` 必须与"两层解的一致性"一起考虑——
benchmark 里比较整模与分阶段时，两条路径用**同一套** `stage1_symmetry`
与 `min_band_width_s`，否则比的是两个不同的模型。

### 5.14 big-M 常量表

#### 5.14.1 一个公式、三个字段

`BigMTable.compute`（`model/meta.py:30`）只做一件事：**按数据规模估一个统一的 M**。

```
M = T_max + 6C + 10
```

`T_max = ctx.max_cum_T_s()`（`preprocess/context.py:95`）是所有**目标需求**里最大的累计行程时间
（各需求 `span_s` 的最大值，即从需求链首到链尾的行程时间，**不是**单段行程时间）。

`BigMTable` 分 `containment` / `plan_activation` / `soft` 三个字段，三者**当前同值**；
留三个字段是为了"将来某一类约束要单独换紧（或换松）时，只改 `compute` 一处、不动所有调用点"。
标准案例（G1：单方案、可调边界、κ = 1）实测：

| C | `T_max` | M |
|---|---|---|
| 83.16 s | 91.137 | 600.10 |
| 140 s | 91.137 | 941.14 |
| 180 s | 91.137 | 1181.14 |

`T_max` 与 C 无关（只由路段长度、速度倍率决定），所以 **M 随 C 近似线性增长**：
C 越大，窗口端点、带起点 u、带宽 β 的界全部按比例变大，M 必须跟着放大。
这也解释了为什么 M 要跟着 C 缩放，而不能写死成一个数：C 从 83s 扫到 180s，M 从 600 涨到 1181。
另外注意 `T_max` 是**按本案例的目标需求**取的：绿波全线需求跨度 ~91s，
而红波相邻对需求（`RW_both_window`）跨度只有 ~18s，于是后者的 M 主要是 `6C` 撑起来的。

#### 5.14.2 三个字段分别被谁消费

| 字段 | 用在哪 | 代码位置 | 局部记法 |
|---|---|---|---|
| `containment` | C5 带的窗口包含（`u + T − φ − ŝ − nC ≥ −M(1−a)`） | `builder.py:1000` | `M` |
| | C5 回绕整数 n 的全局界 | `builder.py:1122` | `M` |
| | C7 多带排序 / 圆环分离 | `builder.py:1157` | `M` |
| | C8_HARD margin 硬下限 | `builder.py:1197` | `M_hard` |
| | C9 红带上游包含（`u + β − φ_up − mC − ŝ_up ≤ τ + M(1−ag)`） | `builder.py:1351` 取值、`1404`/`1410` 使用 | `M` |
| | C9 红带相容**硬**边 | `builder.py:1451` | `M_hard` |
| | C12 模板约束（RHS 是绝对秒时再补 `abs(rhs)`） | `builder.py:847` | `M + abs(rhs) + 1` |
| `soft` | C8 margin 短缺 σ | `builder.py:1244` | `M` |
| | C9 红带相容**软**边 | `builder.py:1450` | `M_edge` |
| | C10 用户软约束的违反量 `σ_c` 上界 | `builder.py:1696` | `M + abs(rhs) + max_abs_atom_bound(3C) + 1` |
| `plan_activation` | —— **当前没有调用点**：C2/C3 的方案激活没有用这个字段，而是走逐约束估算 `_constraint_activation_m`（见 §5.14.4） | — | — |

另外 `builder.py:1232`、`1461`、`1487` 用 `2M` 当作 margin 短缺 / 红边软量 σ 的**技术上界**
（保证变量有界），正常解不会顶到那里。

#### 5.14.3 6C 是怎么来的

big-M 的正确性只有一条要求：

> 当激活变量取 0、这一行被"关闭"时，**M 必须 ≥ 该行两端项在各自变量上下界内可能出现的最大差**；
> M 偏小就会**误切可行解**（解错），M 偏大只会让松弛变松（解慢）。

按被松弛行里出现的项逐项估上界：

| 行里出现的项 | 量级 | 依据 |
|---|---|---|
| 窗口端点 `ŝ` / `ê` | `C` | 端点是"方案名义端点 × `x_p` + `C·z_p` + δ"；标准案例实测上界是 **0.63C（单周期）～1.00C（双周期）** |
| 带起点 `u` | `C` | `u` 的界就是 `[0, C]`（`φ = 0` 的带最多绕一圈） |
| 带宽 `β` | `C` | C6：`β ≤ C·e` |
| 累计行程 `T` | `T_max` | `T_j` 的定义 |
| 余量 | 再留一倍 | 硬/软 margin 与两端松弛同向出现时会有重复计数 |

即"端点 + u + β ≤ 3C，再留一倍余量 ⇒ 6C"，加上 `T_max` 与常数 10。
**注意这是保守估计**：上面每一项都取了整周期 C，而绿波案例的端点实测只有 0.63C（单周期）～1.00C（双周期）；
逐约束估算（`_constraint_activation_m`）给单个原子兜底的 `3C` 更保守。
但"保守"不等于"随便写大就行"——M 越大代价越大（见下表），所以 §5.14.5 还要回头看它**实际用掉了多少**。

反面做法就是把 M 写成 `1e6`。同一案例（G1，C = 140）实测 LP 松弛：

| M 的取法 | 模型里约束系数的最大/最小值 | LP 松弛上界（composite） | LP 迭代数 |
|---|---|---|---|
| 紧 M（941） | 941 | 266.43 | 18 |
| M = 1e6（全局字段 + 逐约束都改成 1e6） | 1e6 | 279.99 | 18 |
| M = 1e9（同上） | 1e9 | 280.00 | 28 |

（该案例 MILP 最优 composite = 41.98，20s 内解到最优；表里 LP 上界与最优值差距很大是模型本身松弛弱，不是 M 的问题。）
读法：M 从 941 放到 1e6，LP 上界从 266.43 涨到 **279.99（+5.1%）**；放到 1e9，LP 迭代从 18 涨到 28。
但这个效应**依模型而定**：红波案例（G4|RW_both_window|D|p5|adj）里 M 取 877 还是 1e6，
LP 上界**完全相同**（1285.97）。所以"别用 1e6"的**主要**理由是上表第二列——
**系数动态范围**从 941 变成 1e6～1e9，单纯形/分支定界的数值精度和 presolve 容差都会变差；
"LP 松弛变松"是可能发生、但不保证的附加代价。

#### 5.14.4 两处比全局 M 更紧的特例

1. **方案内约束的逐约束 M**：`_constraint_activation_m`（`builder.py:381`）不直接用全局 M，
   而是把约束里的每个原子（`boundary` / `window_duration` / `offset` / `bandwidth` / `const`）
   按各自上界估一遍、乘系数求和，最后取 `max(总量, |rhs|) + 1`。
   C = 140 时实测只出现 **421（= 3C+1）** 和 **841（= 6C+1）** 两个值，
   都比全局 M = 941 紧（差的正好是 `T_max + 9`）。
   好处是 C2/C3 的 LP 松弛更强；代价是**每加一种新原子类型，就要在函数里的局部变量 `atom_ub` 上补一条上界，漏了就误切可行解**。
2. **红波回绕整数 `m` 的专用 M**：`MRANGE` 用 `Mm = max(1, m_ub − m_lb) + 1`（`builder.py:1419`）。
   `m` 的跨度只有几，实测该行在盒子上的最大可能违反量只有 **1s**，即"需要的 M"是 1 量级；
   代码给的 `Mm` 实测取 **2 或 3**，而同一案例的全局 `containment` 是 877（C = 140）。
   也就是在这一行上，专用 M 把激活变量的系数从 877 压到 2～3——**差了近三个数量级**，
   等于给 LP 松弛补回一条几乎"不被松弛"的约束。

#### 5.14.5 M 到底够不够：一个随时能跑的体检

验法与 §5.14.3 的判据一一对应：把每条约束行在**变量上下界的盒子里**取最大可能违反量
（`<=` 行取 `max(lhs) − rhs`，`>=` 行取 `rhs − min(lhs)`），再和该行实际用的 M 比。
对 3 个案例 × C ∈ {60, 83.16, 140, 180} × κ ∈ {0.3, 1.0, 1.5} 共 **36 个组合**跑一遍：

| 范围 | 最大利用率 | 出现在哪 |
|---|---|---|
| 只算绿波案例（G1 单周期 / G3 双周期，24 组） | **58.4%** | 全部出现在 C5（最小 39.8%） |
| 加上红波案例（G4\|RW_both_window\|D\|p5\|adj，12 组） | **97.5%** | C9（C = 180、κ = 1.5，违反量 1080s ≈ 6C） |

读法：

+ 没有任何一组超过 100%，也就是 **M 在所有被测组合上都还够用**——这是结论的第一半；
+ 但红波多方案案例上余量只剩 **2.5%**（前 5 紧的组合全是它，利用率 94.7%～97.5%），
  说明 `6C` 这一项不是"随手拍大"，而是**真的被用满了**。这是结论的第二半，也是风险所在。

所以 `T_max + 6C + 10` 对当前数据与参数范围成立，但它**不是无条件安全**的：
`T_max` 只按本案例的目标需求取，红波案例里它只有 ~18s，M 几乎完全由 `6C` 决定。
一旦将来出现"同一条约束里出现更多窗口/边界原子"或"允许相位在整周期内平移"这类新原子，
`6C` 就可能不够。必须重跑这个体检；一旦利用率 > 100%，M 就会切掉可行解，
现场症状是"明明有可行方案却报 infeasible"或目标值莫名偏低。

#### 5.14.6 写新约束时的清单

| 方向 | 症状 | 后果 |
|---|---|---|
| M 偏小 | 利用率 > 100% | **误切可行解**（结果错），通常表现为 infeasible 或目标偏低 |
| M 偏大 | 系数动态范围大 | LP 松弛变松、数值变差、求解变慢（**不改变正确性**） |

正确顺序是**先保证"够"，再尽量"紧"**。新增一条条件激活约束时按三步走：

1. 写出"关闭"时两端差的最坏上界，取它作为 M 的**下界**；
2. 优先复用 `_constraint_activation_m` 的逐约束思路（或像 `MRANGE` 那样算专用紧 M），
   而不是直接抓全局 `containment`；
3. 把新行加进 §5.14.5 的体检，确认利用率 < 100%。

## 6. 目标函数

`ArterialModel.expr_composite`（`builder.py:95`）：

```
composite =  Σ_b weight_b · Σ_q β_{b,q}                    ← 带宽奖励（要最大化）
           − Σ_{绿带} coef · (σ^s + σ^e)                   ← margin 短缺罚
           − Σ_{软约束, owner=composite} coef · σ          ← 用户软约束罚
           + Σ_{均衡组} group.weight · z_g                 ← 均衡组奖励
           − Σ_{红带边界亲和} coef · slack                 ← 红波边界贴合罚

           − pen · deficit                                ← 均衡组 min_existing 短缺罚
                                                            （仅 on_infeasible="skip" 且 pen>0 时）
L (只是记录，不进 composite) = Σ_{软约束, owner=intersection_loss} coef · σ
```

三条设计原则：

1. **单位统一**：所有项都是"秒"，系数无量纲。这样"1 秒带宽 vs 1 秒 margin 短缺"
   的取舍才有可解释的价格。
2. **账本分离**：需要"同时报告带宽和各类损失"的多目标场景，不把所有东西
   揉进一个加权和，而是把损失归到 `L`、用第二阶段的 ε-constraint 扫 Pareto 前沿
   （`pareto/`）：先 `max composite` 得到 `B*`，再对若干 `ε` 求解
   `min L s.t. composite ≥ B* − ε`。这样给出的是一条**前沿**，而不是一个
   拍脑袋的权重。
3. **均衡组**（`builder.py:1570`）：`z_g ≤ Β_b / target_b`（组内需求带宽的
   归一化最小值），把 `weight·z_g` 加进目标 → "两个方向都要好，
   而不是一个方向特别宽、另一个为零"。这是"公平性"的线性化标准做法。

## 7. 约束放松的五种机制（教学重点）

"放松"这个词在这套代码里有五种完全不同的含义，混在一起讲最容易糊涂。

### 7.1 逻辑激活式放松（big-M）：把"如果…就…"写成线性

**用途**：让一条约束**只在某个 0/1 成立时**有效。
**形式**：`lhs ≤ rhs + M(1−z)`，`z ∈ {0,1}`。
**出现位置**：C2 方案内硬约束、C5 窗口包含、C7 多带分离、C13。
**要点**：M 必须紧；`z` 必须是 0/1（或像 `h` 那样被证明是 0/1）。

### 7.2 定价式放松（软约束 + 松弛变量）：把"必须"变成"尽量"

**用途**：允许违反，但按价格惩罚。
**形式**：`lhs ≤ rhs + σ`，`σ ≥ 0`，目标里 `−coef·σ`。
**出现位置**：C3 方案内软约束、C8 margin、C10 用户软约束。
**要点**：`owner` 决定罚项进哪个账本（composite 还是 L）；
报告时要**重算真实违反量**，不要直接读 σ。

### 7.3 硬下限式收紧（有时"放松"的反面才是你要的）

margin 的 `hard_min_s` 把"希望 ≥ δ_min"变成"必须 ≥ hard_min"。
教学意义：**同一件事可以同时有硬版和软版**——硬版保证安全，软版表达偏好。
工程上常见的组合是 `hard_min_s=3, delta_min_s=5, coef=1`：
至少留 3 秒，争取留 5 秒，不够的按秒罚。

### 7.4 组合限制的放松：独占 ↔ 共享

`allow_window_sharing` 是在**两种约束体系之间切换**：

| | 关闭共享（默认） | 打开共享 |
|---|---|---|
| 独占行 | 加 `Σ_q a[b,q,j,k] ≤ 1`：同一个绿窗至多被**该需求**的一条带占用 | 不加这一行 |
| 兜底 | 仍靠 C7 的圆环分离保证该需求的多条带时间不重叠 | 同左（圆环分离始终存在） |
| 连带影响 | `qmax` 被"链上最窄窗口数"封顶（`demand_max_bands`） | 不再用该上限，可按 `max_bands` 开更多带 |
| 解空间 | 略保守（部分路口共用、部分路口不同的最优解会被切掉） | 更完整，但变量/约束更多 |

这是"**放松一条组合限制，代价是模型变大**"的典型权衡。

### 7.5 数值层面的"放松"：让 LP 松弛更紧（性能就是一切）

这一类和上面相反，是**加强**而不是放松，但对求解时间的影响最大：

| 手段 | 位置 | 作用 |
|---|---|---|
| 紧 big-M（按量级估，不用 1e6） | `builder.py:380` | LP 松弛不被拉松 |
| NRANGE 逐槽位收紧 n 的界 | `builder.py:986` | 整数变量界小一个数量级 |
| 逐槽位不可行剪枝 `a ≡ 0` | `builder.py:1022` | 直接删变量 |
| 有效不等式 C13（红波） | `builder.py` 红带段 | 补回 big-M 丢掉的信息 |
| 对称破缺（e 单调、β ≥ w_min e） | `builder.py:961` | 删等价分支 |
| 预处理剔除不可行方案 | `preprocess/feasibility.py` | 减少 x 变量与整棵搜索树 |

### 7.6 求解层面的放松：时间上限与 gap

`SolveOptions(time_limit_s, mip_rel_gap)`（`solve/backend_base.py:38`）。
`time_limit_s` 到点后返回**当时的最优可行解 + 对偶界**，
状态是 `time_limit`（表示"未证最优"，不是"没有解"）。
`mip_rel_gap=0` 表示要求严格最优；>0 时允许"离上界 gap% 就停"。
benchmark 里统一用 20s 上限 + gap 0，并把是否触限当作结果的一部分记录。

## 8. 四个可以手算的例子

下面所有数字都可以用一条命令复现（同一份代码就是这一节的"实验报告"）：

```bash
python examples/tutorial_small_cases.py
```

公共设置：3 路口 `I1→I2→I3`，C = 100s，单方案、边界固定，每段 300m @ 15m/s = 20s，
锚点 `φ_I1 = 0`。

> **先记住一句话，否则手算一定错**：`φ` 是**决策变量**，不是给定的。
> 除锚点（φ=0，纯 gauge）外，每个路口的窗口都能被 `φ` 挪到任意位置。
> 于是"让车的到达时刻落进窗口"这件事，模型主要是靠**挪窗口**去满足的，
> 而不是让带去迁就固定的窗口。手算时若把 φ 当常数，
> 得到的带宽会系统性地偏小（我写这一节时就真实踩了这个坑，
> 第一版手算给出 30s，求解器给出 50s）。

### 8.1 案例 1：单方向带 + φ 全自由 → β = 链上最窄绿窗

配时：I1 绿窗 60s、I2 50s、I3 70s（各一段绿）。一条上行带穿过全线。

求解器结果（`status=optimal`，composite = β = **50s**）：

| 路口 | 绿窗宽 | 到达 | 离开 | 该路口实际用的窗口 | 左余 | 右余 |
|---|---|---|---|---|---|---|
| I1 | 60s | 100.00 | 150.00 | [100.00, 160.00] | 0.00 | 10.00 |
| I2 | 50s | 120.00 | 170.00 | [120.00, 170.00] | 0.00 | 0.00 |
| I3 | 70s | 140.00 | 190.00 | [120.00, 190.00] | 20.00 | 0.00 |

`φ = (0, 70, 20)`，`u = 100`，各节点窗口槽都是 1，`n = (1, 0, 1)`。

**怎么读这组数**：

* **β = 50 = min(60, 50, 70)**：卡在 I2 —— 它的窗口被带占满（左右余量都是 0）；
* 每个路口都被 `φ` 挪到"带正好压在自己窗口里"的位置，
  所以**协调在单条带场景里是免费的**；
* `u = 100 = C`：带起点正好落在周期边界上（`u` 的取值域是闭区间 `[0, C]`）；
* `n = (1, 0, 1)` **不是"走错周期"**，只是账本：I1 的窗口从第 1 个副本取
  （[100,160]），I2 从第 0 个副本取（[120,170]），I3 又回到第 1 个副本
  （[120,190]）。把它们换算成**相位（模 C）**就一目了然：
  I1 相位 0（窗口 [0,60] 的起点）、I2 相位 20（窗口 [20,70] 的起点）、
  I3 相位 40（该路口窗口模 C 是 **[20, 90]**，带占 [40,90]、右端正好贴窗口终点）
  —— 就是同一辆车经过的三个时刻 ✓

### 8.2 案例 2：窗口选择 k 是"每个路口独立挑"

把 I1 改成两段绿（`mask=[T,F,T,F]`，边界 0.05/0.4/0.9）→ 派生窗口槽
槽 1 = 5s、槽 2 = 50s；I2、I3 各 70s。

结果：**β = 50s**，指派 `a = (I1: 槽2, I2: 槽1, I3: 槽1)`。

* 槽 1 只有 5s，若被迫用它带宽上限就是 5s；MILP 直接把它置 0，改用槽 2；
* **不同路口用的槽号可以不同**——这正是 `a[b,q,j,k]` 下标里带 `j` 的原因；
* 一个路口的多个绿段是**候选池**，不是"都要用上"；
* 反过来，如果把 `a` 写成只按带槽索引（不按路口），就会强迫"全链都用第 k 段"，
  本例会得到 β = 5s 的假象。

### 8.3 案例 3：双向冲突——φ 才是稀缺资源

每个路口只有一段绿，同时要求一条上行带和一条下行带（权重都 1）。
实测（单格点 60s 上限、gap=0，全部 `optimal`）：

| 绿窗宽 | 单段行程 τ | Σβ 最优 | β_up | β_down |
|---|---|---|---|---|
| 50s | 20.00s | **50.0** | 50.0 | 0 |
| 50s | 6.67s | **73.3** | 36.67 | 36.67 |
| 70s | 20.00s | **80.0** | 50.0 | 30.0 |
| 70s | 6.67s | **113.3** | 50.0 | 63.33 |

读法：

1. 单方向时能顶到 50（案例 1 的结论）；**双向时 Σβ 也只有 50**——
   一个方向几乎把每个路口的绿窗吃光，另一个方向为 0。原因就是那组 φ
   要同时服务两个方向；
2. 行程越短、绿窗越宽，两个方向越能错开，**Σβ 可以超过单个绿窗的宽度**——
   原因是 **C7 的"窗口独占 / 圆环不重叠"只约束同一条需求内部的多个带槽**
   （`builder.py:1155` 的双重循环在 `for b in band_demands` 之内），
   **不同需求**的带允许在同一个路口、同一个绿窗里时间重叠。
   实测 70s / τ=6.67 那一行：I1 处上行带占相位 [0,50]（第 0 个副本的绿窗），
   下行带占相位 [6.67,70]（第 1 个副本的同一个物理绿窗），
   两条带在同一个物理绿窗里重叠了 43.3s。
   （周期副本 `n` 只是记账，它不会凭空多出绿时。）
3. 这就是干线协调真正的难点：**不在单条带，而在多个需求共享同一组 φ**。
   后来做分解时，"跨路口的 gauge φ"也正好是唯一需要小心处理的耦合量。

### 8.4 案例 4：margin 的价格

在案例 3 的第一行上给两个方向都加 `margin: {delta_min_s: 5, coef: 1}`：

* `composite = 40`；解里**存活的那条带（下行）**左右余量恰好都是 5s（margin 罚为 0），
  上行那条 β = 0（被解码过滤），仍是 §8.3 第一行那个「一个方向吃光绿窗」的互斥现象；
* 40 = 50 − 2×5：**窗口两侧的 margin 直接吃掉可用宽度**；
* 与案例 3 的 50 相比，等于"用 10s 带宽换 margin 达标"；
* 若把带宽权重调大（例如 `weight=5`），模型会反过来宁可吃 margin 罚
  也要保住带宽——**软约束的价格就是这么起作用的**（见 §7.2）。

### 8.5 从这四个案例带走的方法论

1. 先问"φ 自由不自由"：自由 ⇒ 单条带的带宽问题几乎平凡（= 最窄绿窗）；
2. 真正的难度来自**共享 φ 的多个需求**（双向、多带、多 OD），
   这时才出现"谁让谁"的取舍；
3. 手算永远从**相位（模 C）**出发，用 `n` 处理跨周期副本，别把 φ 当常数；
4. 软约束/罚项只要单位统一成秒，就能和带宽直接比价。

## 9. 设计决策记录与常见坑

| # | 坑 / 决策 | 说明 |
|---|---|---|
| 1 | **大 M 用 1e6** | LP 松弛立刻完蛋、HiGHS 可能出现数值告警。本项目按类型估紧的 M，量级 `T_max + 6C + 10` |
| 2 | **窗口端点是变量**（v1 做法） | 需要额外的一致性约束，且和"边界可调"联动复杂。v2 改成"端点是边界的线性表达式" |
| 3 | **常数端点不乘 x_p** | 多方案时 Σ_p 会把常数端点累计成"方案数 × 常数"，窗口被放大（真实 bug） |
| 4 | **建完模型再钉 φ** | n 的区间是用 φ 界推的，改晚了会把最优解卡死（真实 bug，故有 `phi_fix`） |
| 5 | **把 n 写成连续** | 连续会让"相邻周期的窗口区间"并起来 → 过度放松、给出物理上不存在的绿波。`n` 必须是整数 |
| 6 | **掩码首尾同时为绿** | 绿段跨越 0/C 首尾相接，极大段被切断；schema 直接报错要求旋转方案 |
| 7 | **窗口独占以为是"完全无损"** | 只有"所有路口都共用同一窗口"才无损；部分共用时会切掉真实最优（设计文档 §4.7） |
| 8 | **直接读 σ 当报告损失** | σ 可能大于真实违反量，报告用几何重算（`report/solution.py:253`） |
| 9 | **双周期边界范围** | 双周期方案的边界比例声明在 (0, 0.5)，不是 (0,1)；`PLAN_WINDOW` 的 `hi` 跟着变 |
| 10 | **手算/推导时把 φ 当常数** | φ 是决策变量（除锚点），单条带的带宽上限就是最窄绿窗；把 φ 当常数会系统性低估带宽（§8.1 的坑） |
| 11 | **`e=1` 但 `β=0` 的退化带** | MILP 的合法退化最优解，报告/绘图要过滤掉（`solution.py:187`） |

## 10. 从解回到图

求解器返回的是变量值向量，解码链（`report/solution.py:74` `SolutionDecoder.decode`）：

```
x[i,p]        → 每个路口选中的方案（argmax，单方案路口直接取固定方案）
bnd_delta[p,d,y] → 边界秒值 = (pos_r + δ)·C → 重新派生实际绿窗（derived_windows_from_boundary_r）
band u, β, e  → 一条带（e<0.5 或 β≤1e-7 丢弃）
a[b,q,j,k]    → 这条带在每个路口用的是哪个绿窗（argmax over k）→ 时距图上带子落在哪
n[b,q,j]      → 该路口用的是第几个周期副本 → 带子画在哪个周期
marginal σ    → 丢弃，改用几何重算的 margin 损失
```

时距图（`report/` 的绘图模块）因此是这样画的：

* 横轴时间、纵轴累计距离；每个路口画上下行两条灯带（绿=绿窗、红=红窗），
  按周期重复；带子按 `u, β` 与各路口实际窗口画成斜带；
* 图上能直接看出本文讲的所有东西：φ 决定灯带在横轴上的错位、
  可调 δ 决定绿窗宽度、`a` 决定带子压在哪个绿段上。

## 11. 红波与绿波的差异（同源，但有 6 处不同）

先给结论：**两者用的是同一台机器**——"把一个连续时间区间 `[u, u+β]` 塞进某个窗口"
+ 0/1 指派 + 整数周期下标 + big-M 条件激活。所以本文 §1–§7 的推导几乎可以照搬。
真正需要单独记住的是下面 6 条差异，其中 §11.4 那条最容易踩坑（它决定时距图怎么画）。

### 11.1 同源的部分

| 维度 | 绿波 | 红波 |
|---|---|---|
| 带变量 | `u`、`β`、`e`、带槽 `q` | 同名同界（`rw_start` / `rw_width` / `rw_on`） |
| 指派 | `a[b,q,j,k]`（每个节点一个 0/1） | `ag` + `ar`（见 §11.5） |
| 包含约束 | 两条（挂 `M(1−a)`） | 两条上游 + 两条下游（挂 `M(1−ag)` / `M(1−ar)`） |
| 存在性 | `β ≤ C·e` | 同（代码归 `C9`） |
| 圆环时间分离 | `C7` 三条（排序 + 不重叠 + 绕回不压） | `C9` 两条 + `SYM` 一条排序行（同样不允许同需求两条带重叠） |
| 对称破缺 / 最小带宽 | `SYM`（`e` 单调、`β ≥ w_min·e`） | 同（label 里带 `red`） |
| 目标 | `Σ w·β` 进 composite | 同 |
| 文档编号 | C4–C8 | C9、C13 |

### 11.2 差异 1：红窗不是配出来的，是绿窗的**补集**

红波没有任何"红相位边界/红掩码"配置——它的窗口由**选中方案的绿窗补集**现算
（`RedWindowBuilder`，`windows.py:150`）。设下游路口某方向有 K 个派生绿窗
（`[ŝ_1,ê_1], …, [ŝ_K,ê_K]`，按周期顺序），则红窗有 2K−1 段：

```
gap 段  rid = 1 … K−1 :  [ ê_r , ŝ_{r+1} ]        可用性 = h_{r+1}
wrap 段 rid = K … 2K−1:  [ ê_r , ŝ_1 + C ]        可用性 = h_r − h_{r+1}
```

三个直接推论：

* 红波的形状**完全由配时方案的 `green_mask` 决定**（改绿掩码就改红窗）；
* **wrap 段必须显式生成**（`ê_r` 到 `ŝ_1 + C`），否则跨 0/C 的红波根本写不出来——
  这也是 §4.2 那条"绿掩码首尾不能同时为绿"的硬校验的动机之一；
* 红窗的可用性是 `h` 的**组合**（`h_r − h_{r+1}` = "第 r 段绿存在、第 r+1 段不存在"
  ⇒ r 是最后一段绿 ⇒ 后面那段红跨 0/C），这就是 §4.4.2 里说"`h` 建成变量便于复用"
  的原因。

### 11.3 差异 2：红波只能存在于**相邻路口之间**

* 校验规则 **V4** 强制 red demand **恰好 2 个节点**（`schema/validation.py:262`），
  且节点必须相邻（V5）；
* 绿波可以跨全线（≥2 个节点，标准案例里是 6 个）。

原因在模型的"两侧结构"：红带的上游一侧容器是**绿窗**、下游一侧容器是**红窗**。
两个节点时正好"上游绿 → 下游红"；要跨三个以上路口，就得写成
"绿—红—绿—红"交替，这与当前"上游只挂 `ag`、下游只挂 `ar`"的因式分解形式不匹配。
所以实现上把它限制成相邻对：**一条红波需求 = 一个相邻对的一个方向**。

### 11.4 差异 3：`u` 的锚点不同（最容易踩的坑）

| | 绿波 | 红波 |
|---|---|---|
| `u` 是什么 | 带前缘到达**链首（上游端）**的时刻 | 带前缘到达**下游路口**的时刻 |
| 另一个路口 | `u + T_1`（链首 `T_0 = 0`） | `u − τ`（上游，再按整数 `m` 平移周期） |

把两条包含式写出来对比（方向 d，上游 `up`、下游 `down`，行程时间 τ）：

```
绿波（节点 j 用窗口槽 k，周期下标 n）：
    u + T_j        ≥ φ_{I_j} + ŝ_{I_j,k} + n·C
    u + T_j + β    ≤ φ_{I_j} + ê_{I_j,k} + n·C

红波：
  下游（只挂 ar，周期偏移 k）：
    u              ≥ φ_down + red_start_r + k·C
    u + β          ≤ φ_down + red_end_r   + k·C
  上游（只挂 ag，周期下标 m）：
    u − τ          ≥ φ_up + ŝ_{up,g} + m·C
    u + β − τ      ≤ φ_up + ê_{up,g} + m·C
```

也就是说：带在**下游**落在**红窗**里、在**上游**落在**绿窗**里，
而 `u` 站在下游那一侧。物理含义就是经典的"红波"：
**上游绿灯期间通过的车队，正好在下游红灯期间到达**（要停/排队的那一队）。

**这个差异会直接影响画图**：红带不能像绿带那样按 `u + T_j` 画。
时距图里红带是**重建**出来的——`_red_band_display_times`（`report/diagram.py`）
的注释写得很明确：

> The downstream interval is `[u, u+width]`. The corresponding upstream
> departure interval must be `[u − tau, u + width − tau]` plus an integer number
> of cycles.

它会在 ±8 个周期副本里搜索"上下游都落在真实窗口内"的那一份来画，
因为原始解里的 `k`、`m` 只是记账下标，直接画会出现斜率反向的假象。

### 11.5 差异 4：指派因式分解成 `ag` + `ar`

| | 绿波 | 红波 |
|---|---|---|
| 上游/单侧指派 | `gw_win[b,q,node,slot]`（每节点一个 0/1，跨节点共用一个 `gw_cycle`） | `rw_up_win[b,q,upslot]`（上游绿窗槽） |
| 下游指派 | —— | `rw_down_win[b,q,rid,cshift]`（下游红窗槽 + 周期偏移） |
| 周期下标 | `gw_cycle[b,q,node]` 每节点一个整数 | `rw_up_cycle[b,q]`（上游整数，与 `gw_cycle` 对称）；下游的周期偏移已折进 `rw_down_win` |
| 指派合计 | `Σ_k a = e` | `Σ_g ag = e` 且 `Σ_{r,k} ar = e` |
| 可用性 | `a ≤ h` | `ag ≤ h_up`，`ar ≤ red_avail` |

**为什么可以因式分解**：老写法是联合 0/1 变量 `aR[g,r,k]`（同时选上游绿窗 g 与下游红窗实例 (r,k)）。
但约束里从来不需要引用"配对本身"——`ag=1` 与 `ar=1` 激活的恰好是同一组四条不等式
（上游两条 + 下游两条），所以拆成两组变量**可行域不变**，变量数却从
`|G|×|R|×|K|` 降到 `|G| + |R|×|K|`。

**代价与补偿**：因式分解后"`β` 不超过所选窗口宽度"这层信息在 LP 松弛里被 big-M 拉松了，
因此红波必须补 **C13 两条有效不等式**（§5.12）：

```
β ≤ Σ_g W_g · ag[q,g]            + C(1−e)
β ≤ Σ_{r,k} Wr_{r,k} · ar[q,r,k] + C(1−e)
```

绿波没有这一步：它的回绕整数 `n` 已经有 NRANGE 的紧界，松弛质量够用。

顺带一个实现细节：因式分解后先算"兼容对集合"，再投影出 `ag_slots` 与
`ar_keys`（`_red_compatible_keys`），把不可能配对的变量直接不建——
所以红波的 `ag`/`ar` 通常远少于理论个数。**`m` 的区间也按上游窗口槽分别推导**
（`_red_upstream_wrap_bounds`），并且用**紧的**专用 big-M `Mm`（`m` 的跨度只有几），
而不是全局 containment M（`builder.py:1418`）。

### 11.6 差异 5：目标里的"损失项"从 margin 换成**边界亲和**

* **红波没有 margin**：margin 变量只在 `_build_green_bands` 里创建
  （`margin` 是绿波专属，设计文档 C8 明确写"仅绿带；红带无 margin"）；
* 取而代之的是 **`C9_RED_EDGE` 边界亲和损失**：希望红带的起点贴住上游绿窗起点、
  终点贴住上游绿窗终点：

```
gap_start = u − (φ_up + ŝ_g + τ)          ← 红带起点比上游绿窗起点晚多少
gap_end   = (φ_up + ê_g + τ) − (u + β)    ← 红带终点比上游绿窗终点早多少
```

两者都希望 ≈ 0；超出 `free_s` 的部分乘 `coef` 罚进 composite，
还可以用 `hard_max_s` 加硬上限（`C9_RED_EDGE_HARD`）。
标准案例的默认配置是 `red_boundary_default: {start: {free_s: 3.0, coef: 0.2}, end: null}`
——即"红带起点前 3 秒免费，之后每秒罚 0.2"。

另一个编码差异：**红波边界罚在报告里是直接读 slack 变量值的**
（`report/solution.py:217-232`），而绿波 margin 是解码后**几何重算**的
（§5.10）——因为红波的 slack 只挂在 `ag` 上、结构简单，不会被"未选中窗口"污染。

### 11.7 差异 6：带槽数上限的来源不同（以及没有窗口独占行）

| | 绿波 | 红波 |
|---|---|---|
| 槽数上限 | `min(max_bands, chain_max)`，`chain_max` = 链上各路口**绿段数的最小值** | `max(1, max_bands or 3)`（默认 3），**不受 `chain_max` 裁剪** |
| 窗口独占行 | `allow_window_sharing=False` 时有 `Σ_q a[b,q,j,k] ≤ 1` | **没有**这类行，只靠圆环时间分离 |

原因：绿波的 `chain_max` 是"结构上限"（一个路口周期里只有 1 段绿，就不可能有 2 条
时间不重叠的带都从这一个绿段穿过）；而红窗是**绿窗的补集**，它的数量与"绿段数"
不是同一个额度，所以红波按 `max_bands`（默认 3）放开。

### 11.8 一张表总结

| # | 差异 | 绿波 | 红波 | 影响 |
|---|---|---|---|---|
| 1 | 窗口来源 | 由 `boundaries`+`green_mask` 派生 | **绿窗的补集**（gap + wrap，2K−1 段） | 红波形状完全跟随配时方案；wrap 段必须显式生成 |
| 2 | 跨度 | 可跨全线 | **只能相邻对**（V4 恰好 2 节点） | 红波是"逐段"的局部需求 |
| 3 | `u` 的锚点 | 链首（上游端） | **下游路口**（上游是 `u − τ` + 整数 `m`） | 画图必须重建（`_red_band_display_times`） |
| 4 | 指派变量 | 单个 `gw_win` + `gw_cycle` | 因式分解 `rw_up_win` + `rw_down_win`（含周期偏移）+ `rw_up_cycle` | 需补 C13 两条有效不等式 |
| 5 | 损失项 | margin（软/硬） | **边界亲和** `C9_RED_EDGE`（free_s + coef，可选 hard_max_s） | 目标里两类项的单位都是秒，可比价 |
| 6 | 槽数上限 / 独占 | `min(max_bands, chain_max)`，有窗口独占行 | `max(1, max_bands or 3)`，无独占行 | 红波能开的带槽更"自由" |

### 11.9 一句话理解

绿波回答"怎么让车一路不停"，红波回答"怎么让车在该停的地方停"。
两者在数学上是同一件事——**把一个连续区间塞进一个窗口**——
所以本文前面所有推导（含 §7 的五种放松机制）都能照搬到红波；
差别只在"窗口从哪来、锚点在谁身上、指派变量怎么拆"。
