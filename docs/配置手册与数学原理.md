# 干线绿波 / 红波协调优化 MILP — 配置手册与数学原理

> **v2 重要变更：相位边界建模。**
> 输入不再使用 `windows`；每个 `plan.directions[d]` 用
> `boundaries: [{pos_r, adjust}]` + `green_mask` 声明。
> 绿灯窗口和红窗都是派生量；`min_phase_s` 默认 1e-3。
> 旧版 `windows` / `endpoint` 原子已废弃。

本文档面向算法工程师、后端工程师和交通信号配时工程师，目标是解释：

1. 输入 JSON 中每一个可配置对象的作用；
2. 每个字段的物理意义和单位；
3. 这些配置最终如何进入 MILP；
4. 背后的数学模型、变量、约束和目标函数；
5. 求解流程、解的结构、求解器特性以及如何调试。

> 本实现与《干线绿波红波协调优化MILP设计文档》保持一致，但在以下工程细节上做了明确实现：
> - 使用冻结 dataclass 代替 pydantic，以避免额外依赖；
> - 为处理周期回绕，带窗口匹配整数 `n` 允许取负值；
> - 红波带指派因式分解为 `ag`（上游绿窗）与 `ar`（下游红窗实例，含周期偏移 `k`），并用时间分离约束替代实例独占；
> - 距离支持上下行分别配置。

# 1. 最小示例与运行方式

## 1.1 Python API

```python
import json
from greenwave import run

with open("examples/minimal_problem.json", encoding="utf-8") as f:
    problem = json.load(f)

result = run(problem)
print(result["grid_results"])
print(result["pareto"]["points"][0]["solution"]["bands"])
```

`run()` 的输入是一个普通 `dict`，返回值是可直接 JSON 序列化的结果字典。

## 1.2 命令行

```bash
python -m greenwave examples/minimal_problem.json \
    --out examples/minimal_result.json \
    --diagram-dir examples/diagrams
```

```bash
python examples/generate_diagrams.py      # 生成 6 张时距图
python examples/generate_pareto.py        # 生成 1 张 Pareto 前沿图
```

# 2. 输入对象的总体结构

完整输入 JSON 的顶层字段：

```json
{
  "corridor": { ... },             // 干线拓扑、路段长度、速度
  "plans": [ ... ],                // 每个路口的候选信控方案
  "objective": { ... },            // 带需求、margin、Pareto 配置
  "grid": { ... },                 // 周期、速度倍率格点
  "solver": { ... },               // 求解器配置
  "global_constraints": [ ... ],   // 可选的模型级硬/软约束
  "constraint_templates": [ ... ]  // 可选的按 plan/window 展开的约束模板
}
```

对象关系：

```text
ProblemInput
├── CorridorSpec
│   ├── intersections: 有序路口 id 列表
│   └── segments: 相邻路口之间的路段
├── PlanSpec[]
│   ├── intersection: 所属路口
│   ├── directions: 每方向 boundaries + green_mask
│   ├── min_phase_s: 最小相位数值保护
│   ├── hard_constraints
│   └── soft_constraints
├── ObjectiveConfig
│   ├── BandDemandSpec[]
│   ├── margin_default
│   └── ParetoConfig
├── GridConfig
├── SolverConfig
├── ConstraintSpec[]        // global_constraints
└── ConstraintTemplate[]    // 按 scope 展开
```

> 核心抽象（v2）：算法层看不到路口内部相位相序，只看到每个方案在每个方向上的
> **相位边界**与 `green_mask`；绿灯窗口是这些边界的极大连续绿区间派生量。
> 边界本身是一等变量，可以被任意约束引用。

# 3. Corridor：干线配置

## 3.1 示例

```json
{
  "corridor_id": "demo",
  "intersections": ["I1", "I2", "I3"],
  "segments": [
    {
      "from": "I1", "to": "I2",
      "distance_m": 500.0,
      "distance_up_m": 520.0,
      "distance_down_m": 480.0,
      "speed_up_mps": 11.1,
      "speed_down_mps": 10.5
    }
  ]
}
```

## 3.2 字段说明

### `corridor_id`

干线的唯一标识，仅用于日志、报告和调试。无物理意义，但建议全局唯一。

### `intersections`

- 类型：字符串数组；
- 物理意义：沿干线**物理顺序**排列的路口 id；
- 第一个路口是全局参考锚点，求解时固定 `φ = 0`；
- 数组长度记为 `N`；
- 需求中的 `nodes` 必须来自该数组。

### `segments`

- 数量必须为 `N - 1`；
- `segments[i]` 连接 `intersections[i]` 与 `intersections[i+1]`；
- `from` / `to` 必须与相邻两个路口一致。

## 3.3 路段距离：兼容旧字段与分方向字段

### 旧格式：双向等长

```json
{"from": "I1", "to": "I2", "distance_m": 500.0, ...}
```

此时：

```text
distance_up   = distance_m
distance_down = distance_m
```

### 新格式：上下行分别配置

```json
{
  "from": "I1", "to": "I2",
  "distance_up_m": 520.0,
  "distance_down_m": 480.0,
  ...
}
```

此时上下行行程时间分别使用各自长度。

### 混合格式

```json
{
  "from": "I1", "to": "I2",
  "distance_m": 500.0,
  "distance_up_m": 520.0,
  ...
}
```

规则：

- 若 `distance_up_m` 存在，上行使用它；
- 否则回退到 `distance_m`；
- 下行同理；
- 若两个分方向和公共值都缺失，校验报错。

实现接口：

```python
SegmentSpec.distance_for("up")    # -> float
SegmentSpec.distance_for("down")  # -> float
CorridorSpec.distance_m(seg_index, "up")
```

## 3.4 速度

- `speed_up_mps`：上行设计速度，米/秒；
- `speed_down_mps`：下行设计速度，米/秒；
- 实际速度 = 设计速度 × 格点速度倍率 `κ`。

## 3.5 行程时间与累计行程时间

对方向 `d ∈ {up, down}`，路段 `i` 的行程时间：

```text
τ_i^d = distance_i^d / (κ · speed_i^d)
```

对带需求链上的第 `j` 个节点，从链首开始累计：

```text
T_1 = 0
T_j = T_{j-1} + τ_{j-1}^{d_b}
```

其中：

- `τ` 的单位是秒；
- `T_j` 是输入带从链首出发到第 `j` 个路口的累计行程时间；
- `τ`、`T` 在每个格点 `(C, κ)` 内是常数。

物理意义：如果带在链首的起点为 `u`，那么它在第 `j` 个路口的到达时间为：

```text
u + T_j
```

这是绿波带 C5 约束的核心。

## 3.6 校验点

- 速度必须为正；
- 距离（公共或任一方向解析后）必须为正；
- 路段数量必须为 `N-1`；
- 路口 id 至少出现一次，不能有孤立路口。

# 4. Plan：信控方案配置（v2 相位边界）

## 4.1 示例

```json
{
  "id": "I1_P1",
  "intersection": "I1",
  "double_cycle": false,
  "min_phase_s": 0.001,
  "directions": {
    "up": {
      "boundaries": [
        {"pos_r": 0.2, "adjust": [-0.02, 0.02]},
        {"pos_r": 0.6}
      ],
      "green_mask": [true, false, true, false]
    },
    "down": {
      "boundaries": [{"pos_r": 0.5}],
      "green_mask": [true, false]
    }
  },
  "hard_constraints": [],
  "soft_constraints": []
}
```

## 4.2 `directions` / `boundaries` / `green_mask`

- `boundaries`：方向内的有序相位边界，比例域，严格递增；
  - 单周期在 `(0, 1)`；
  - 双周期在 `(0, 0.5)`，展开时自动加入 0.5 和复制边界。
- `green_mask`：长度 = 边界数 + 1，标记每个相邻边界区间对干线该方向是否绿灯。
  - 方案内固定；不同绿灯组合就是不同方案。
  - 一个方向必须同时有绿区间和红区间。
  - 首尾区间不能同时为绿；如果有这种情况，用户需要在输入前轮转周期。
- 绿灯窗口 = 极大连续绿区间的并（派生量）；
- 红窗 = 整周期补集中的极大连续非绿区间（派生量），允许跨 0/C 和双周期的 0.5。
- 单个相位可以隐藏在绿灯窗口内部：边界仍然存在，可以被 `boundary` 原子引用和约束。

## 4.3 边界微调 `adjust`

`adjust` 直接写在边界对象里：

```json
{"pos_r": 0.2, "adjust": [-0.02, 0.02]}
```

- 单位是周期比例偏移；
- 必须满足 `lo <= 0 <= hi`；
- 未声明 `adjust` 的边界固定。

## 4.4 `min_phase_s`

- 默认 `1e-3` 秒，主要用于吸收 MILP 容差，防止边界粘在一起或数值上轻微颠倒；
- 用户应按业务配置有意义的最小相位（如 5s）；
- 对每一条相邻 edge 生效，包括周期边和双周期的 0.5 seam。

## 4.5 `double_cycle`

- 边界在半周期 `(0, 0.5)` 内声明；
- 展开为 `{b_j} ∪ {0.5} ∪ {b_j + 0.5}`；
- 复制边界复用同一个 δ，因此一致性是结构性的，不需要额外等式；
- 每个半周期内部独立派生绿窗；红窗按整周期补集派生。

## 4.6 方案内约束

- `hard_constraints` / `soft_constraints` 的原子：
  - `boundary`：引用声明边界 `index`（0-based）；
  - `window_duration`：引用派生绿窗下标；
  - `red_duration`：引用 plan-native 红窗 `rid`（1-based）；
  - `const` / `offset`。
- 旧 `endpoint` 原子已废弃。
- `boundary` 秒值 = `(pos_r + δ) × C`。
- 软约束违反量 × `coef` 计入 `intersection_loss` 或 `composite`。

# 5. BandDemand：绿波/红波需求配置

## 5.1 示例

```json
{
  "id": "GW_up_full",
  "type": "green",
  "direction": "up",
  "nodes": ["I1", "I2", "I3", "I4"],
  "max_bands": null,
  "weight": 1.0,
  "margin": {"delta_min_s": 2.0, "coef": 1.0}
}
```

## 5.2 `type`

- `"green"`：绿波带需求；
- `"red"`：红波带需求。

绿波带：

- 链式带，`nodes` 长度 ≥ 2；
- 带必须连续穿过链上每个路口的一个绿灯窗口；
- 带宽由链上最紧窗口决定。

红波带：

- 只在**相邻两个路口**之间定义；
- `nodes` 长度必须恰好为 2；
- 上游一个绿灯窗口平移旅行时间 `τ` 后，与下游一个红灯区间的重叠。

## 5.3 `direction` 与 `nodes`

`nodes` 必须按行驶方向排序：

- 上行：按干线物理顺序，如 `["I1", "I2", "I3"]`；
- 下行：反序，如 `["I3", "I2", "I1"]`。

必须满足：

- 节点存在于 C 干线；
- 顺序单调；
- 节点在物理上连续，中间不跳路口。

## 5.4 `max_bands`

- `null`：
  - 绿带自动取链上各路口可行方案最大窗口数的最小值；
  - 红带默认 3；
- 整数：用户指定；
- 对绿带，实际槽数会同时受“用户指定”和“链上最小窗口数”限制；
- 全单窗口方案时自动退化为 1 条带。

物理意义：一个周期内最多允许几条独立带同时存在。多条带可以用于多个车队、多个方向或多次通行。

## 5.5 `weight`

- 该需求聚合带宽在 composite 目标中的权重；
- 默认 1.0；
- 例如双向绿波中，可以让上行的权重高于下行。

## 5.6 `margin`

仅绿波带有效：

```json
{"delta_min_s": 2.0, "coef": 1.0}
```

- `delta_min_s`：期望的端点净距（秒）；
- `coef`：短缺罚系数；
- 带宽区间到所用绿灯窗口左/右端点的距离不足 `delta_min_s` 的部分，乘以 `coef` 计入目标减项；
- 红波带没有 margin。

物理意义：避免带宽贴着绿灯窗口边界，给排队、检测误差、驾驶行为留出安全裕量。

若需求中没有 `margin`，使用 `ObjectiveConfig.margin_default`。

# 6. ObjectiveConfig：目标与 Pareto 配置

## 6.1 示例

```json
{
  "band_demands": [ ... ],
  "margin_default": {"delta_min_s": 2.0, "coef": 1.0},
  "pareto": {"num_points": 4, "relax_max": 0.3, "topk_grids": 1},
  "allow_window_sharing": false
}
```

## 6.2 `band_demands`

所有要优化的带需求，可以同时包含：

- 全局绿波；
- 窗口绿波；
- 双向绿波；
- 红波；
- 多个局部带需求。

目标会对所有需求求和：

```text
composite = Σ_b weight_b · Σ_q β_{b,q}
          − Σ_{green, margin} coef_m · (σ_left + σ_right)
          − Σ_{soft, owner=composite} coef_c · σ_c
```

## 6.3 `margin_default`

当某个带需求没有显式 `margin` 时使用的默认 margin。

## 6.4 `pareto`

两阶段 ε-constraint 配置：

```json
{"num_points": 4, "relax_max": 0.3, "topk_grids": 1}
```

- `num_points`：ε 扫描点数，实际会生成 `num_points + 1` 个点（包含 ε=0）；
- `relax_max`：最大放宽比例；
- `topk_grids`：阶段 1 最优的 top-k 格点进入阶段 2。

第 `l` 个点的放宽量：

```text
ε_l = (l / num_points) × relax_max × |B*|
```

其中 `B*` 是阶段 1 该格点的最优 composite。

## 6.5 `allow_window_sharing`

- 默认 `false`：同一需求的多条带在同一路口不能使用同一窗口槽位；
- `true`：关闭窗口独占，改为“如果使用同一窗口槽位，则带在时间上不能重叠”的条件析取约束。

默认独占轻微保守，但能显著减小 MILP 规模。

## 6.6 `balanced_groups`：均衡组目标

默认的 band objective 是“所有带宽加权求和最大”：

```text
maximize  Σ_b weight_b · Σ_q β_{b,q}
```

这种目标可能出现“一个方向特别宽、另一个方向很窄甚至为零”的结果。
如果你希望组内每个需求的带宽都不要太小，可以使用均衡组：

```json
{
  "balanced_groups": [
    {
      "id": "balance_up_down",
      "demands": ["GW_up", "GW_down"],
      "weight": 5.0,
      "on_infeasible": "zero",
      "targets_s": {"GW_up": 30.0, "GW_down": 20.0},
      "min_existing": 2,
      "min_existing_penalty_s": 0.5
    }
  ]
}
```

### 数学形式

对每个均衡组 `g`，引入变量 `z_g`，它表示组内需求“归一化总带宽”的最小值：

```text
z_g ≤ Β_b / target_b      ∀ b ∈ G_g
```

当所有 `target_b = 1s` 时，`z_g` 就是绝对秒数带宽的最小值；
当 `target_b` 不是 1 时，`z_g` 是相对目标值的比例。

目标函数中增加加权项：

```text
+ weight_g · z_g
```

因此最终的 composite 是“求和目标”和“均衡组目标”的加权和：

```text
composite = Σ_b weight_b · Β_b
          + Σ_g weight_g · z_g
          − margin 罚
          − composite 软约束罚
```

### `on_infeasible`：均衡组内有带不可行怎么办

这是一个语义不确定点，实现提供两种策略，默认严格模式：

1. `"zero"`（默认，严格模式）
   - 只要组内任意需求不存在，整组 `z_g = 0`；
   - 优点：语义稳、可预测，明确表示“均衡不成立”；
   - 缺点：无法区分“只差一个成员”和“全都不存在”。

2. `"skip"`（跳过模式）
   - 只对存在的需求取最小值；
   - 如果所有需求都不存在，则 `z_g = 0`；
   - 陷阱：求解器可能故意牺牲最难做的成员来抬高其余成员的最小值。

因此 `skip` 模式建议配合 `min_existing` 软约束使用：

```json
{
  "id": "balance_up_down",
  "demands": ["GW_up", "GW_down"],
  "weight": 5.0,
  "on_infeasible": "skip",
  "min_existing": 2,
  "min_existing_penalty_s": 0.5
}
```

含义：

```text
deficit_g >= min_existing - Σ_b y_b
```

目标函数中减去：

```text
min_existing_penalty_s · deficit_g
```

这是软约束，不会破坏“过滤后 MILP 恒可行”的不变式。

### `targets_s`：归一化均衡

默认 `z_g <= Β_b`，即所有成员按绝对秒数均衡。
如果希望表达比例目标，例如“上行 30s : 下行 20s”：

```json
{
  "demands": ["GW_up", "GW_down"],
  "targets_s": {"GW_up": 30.0, "GW_down": 20.0}
}
```

则约束变成：

```text
z_g <= Β_b / target_b
```

此时 `z_g` 表示“相对于目标值的比例”。
默认所有 `target_b = 1.0`，即绝对均衡。

### 需求层次与模型实现

- `z_g` 是连续变量，加入 composite 目标；
- 每个成员用二进制 `y_b` 表示“该需求是否存在”；
- `y_b` 通过 

```text
y_b >= e_{b,q}
y_b <= Σ_q e_{b,q}
```

精确表示“至少有一条带存在”；
- 阶段 2 不需要特殊处理：`z_g` 随 composite 一起进入 ε 约束。

### 需求总带宽的定义

当前实现中，组内每个需求的带宽取：

```text
Β_b = Σ_q β_{b,q}
```

也就是该需求的多个带槽宽度之和。如果某需求只有 1 条带，
那么 `Β_b` 就是那条带的宽度。

# 7. ConstraintExpr：约束表达式系统

## 7.1 结构

```json
{
  "id": "c1",
  "terms": [
    {"atom": {"kind": "offset", "intersection": "I2"}, "coef": 1.0},
    {"atom": {"kind": "bandwidth", "demand": "GW_up_full"}, "coef": -1.0},
    {"atom": {"kind": "const", "const": 30.0}, "coef": 1.0}
  ],
  "sense": "<=",
  "rhs": 30.0,
  "hard": true
}
```

或者软约束：

```json
{
  "id": "c_soft",
  "terms": [ ... ],
  "sense": "<=",
  "rhs_ratio": 0.42,
  "hard": false,
  "soft": {"coef": 5.0, "owner": "composite"}
}
```

## 7.2 原子种类

| kind | 必填字段 | 含义 | 单位 |
|---|---|---|---|
| `offset` | `intersection` | 路口偏置 `φ_i` | 秒 |
| `boundary` | `intersection`, `plan`, `direction`, `index` | 方案相位边界秒值 `(pos_r + δ)·C` | 秒 |
| `window_duration` | 方案内：`direction`, `window`；模板中可留空由 scope 填充 | 派生绿窗持续时间 | 秒 |
| `red_duration` | 方案内：`direction`, `window`；模板中可留空由 scope 填充 | plan-native 红窗持续时间，`window` 是 `rid` | 秒 |
| `bandwidth` | `demand` | 某带需求的聚合带宽 `Σ_q β` | 秒 |
| `const` | `const` | 常数 | 秒 |

## 7.3 `boundary` 原子

```json
{
  "kind": "boundary",
  "intersection": "I1",
  "plan": "I1_P1",
  "direction": "up",
  "index": 1
}
```

边界秒值：

```text
(pos_r + δ) × C
```

其中：

- `index`：声明边界下标，0-based；
- `pos_r`：名义比例；
- `δ`：可调偏移（未声明 `adjust` 时为 0）；
- `C`：当前格点周期。

派生窗口端点可以用两个 `boundary` 原子之差表示；跨 0/C 的窗口终点额外加一个周期 C。

## 7.4 `hard` 与 `soft`

- `hard: true`：硬约束，必须给 `rhs` 或 `rhs_ratio`；
- `hard: false`：软约束，必须给 `soft.coef` 和 `soft.owner`；
- `soft.owner`：
  - `"composite"`：违反量从 composite 中扣除；
  - `"intersection_loss"`：违反量计入路口损失 `L`。

## 7.5 `rhs`、`rhs_unit`、`rhs_s`、`rhs_ratio`

推荐统一写法：

```json
{"rhs": 12.0, "rhs_unit": "s"}
```

或：

```json
{"rhs": 0.42, "rhs_unit": "ratio"}
```

- `rhs_unit = "s"`：绝对秒，网格切换 `C` 时保持不变；
- `rhs_unit = "ratio"`：周期比例，建模时换算为 `rhs × C`；
- 不写 `rhs_unit` 时，`rhs` 默认按秒处理，兼容旧 JSON；
- `rhs_s` 等价于 `rhs + rhs_unit="s"`；
- `rhs_ratio` 等价于 `rhs + rhs_unit="ratio"`；
- 同一个约束中 `rhs` 与 `rhs_s/rhs_ratio` 不能同时出现。

## 7.6 违反量定义

- `expr ≤ rhs`：违反量 = `max(0, expr − rhs)`；
- `expr ≥ rhs`：违反量 = `max(0, rhs − expr)`；
- `expr = rhs`：拆成 `≤` 和 `≥` 两个方向分别计算违反。

## 7.7 作用域

- **方案内约束**：可以引用 `boundary`、`window_duration`、`red_duration`、`const`、`offset`，`plan` 必须等于当前方案；
- **全局约束**：不得引用 `boundary` / `window_duration` / `red_duration`，因为它们归属于某个方案；
- 全局约束可以引用 `offset`、`bandwidth`、`const`。

## 7.8 `constraint_templates`：按作用域展开的约束

当一条约束需要应用到“所有路口、所有方向、所有窗口”时，使用 `constraint_templates`，而不是手写每个 plan。

例如所有绿灯持续时间硬下限 8s，低于 12s 开始计路口损失：

```json
{
  "constraint_templates": [
    {
      "id": "all_green_min_hard",
      "scope": {"kind": "all_plan_windows", "directions": ["up", "down"]},
      "terms": [{"atom": {"kind": "window_duration"}, "coef": 1.0}],
      "sense": ">=",
      "rhs": 8.0,
      "rhs_unit": "s",
      "hard": true
    },
    {
      "id": "all_green_min_loss",
      "scope": {"kind": "all_plan_windows", "directions": ["up", "down"]},
      "terms": [{"atom": {"kind": "window_duration"}, "coef": 1.0}],
      "sense": ">=",
      "rhs": 12.0,
      "rhs_unit": "s",
      "hard": false,
      "soft": {"coef": 8.0, "owner": "intersection_loss"}
    }
  ]
}
```

`scope` 字段：

- `kind`：`all_plan_windows`（绿窗时长）、`all_plan_red_windows`（红窗时长）、`all_windows_of_plan`、`specific_plan_windows`、`all_plans`；
- `directions`：要展开的方向；
- `plan_ids`：限定方案；`all_windows_of_plan` / `specific_plan_windows` 必填；
- `window_indices`：绿窗模板按派生窗口下标筛选，红窗模板按 `rid` 筛选；`specific_plan_windows` 必填；
- `skip_double_cycle_copies`：双周期方案是否跳过复制窗口，默认 `true`。

建模器会在当前格点、当前可行方案上展开模板；多方案路口用方案选择变量 `x` 做 big-M 激活，单方案路口直接加约束。红窗模板用红窗可用性表达式激活，并自动跳过名义时长为 0 的 `(0,0)` 退化红窗区间。

# 8. GridConfig：周期与速度格点

## 8.1 示例

```json
{
  "cycles_s": [70, 80, 90, 100, 110, 120],
  "speed_ratios": [0.9, 1.0, 1.1]
}
```

## 8.2 物理意义

- `cycles_s`：公共信号周期候选值，单位秒；
- `speed_ratios`：设计速度倍率 `κ`；
- 每个 `(C, κ)` 组合称为一个格点；
- 在格点内，所有行程时间 `τ`、累计时间 `T`、窗口秒值都是常数；
- 因此模型内没有双线性项，除方案选择二进制 × 微调量用 McCormick 线性化。

## 8.3 格点遍历

算法会：

1. 对每个格点做方案可行性过滤；
2. 不可行格点直接跳过并记录诊断；
3. 可行格点先跑贪心初始解；
4. 按贪心分数排序后跑阶段 1 MILP；
5. 综合所有格点的 `B*`，取 top-k 进入阶段 2。

# 9. SolverConfig：求解器配置

## 9.1 示例

```json
{
  "backend": "scipy",
  "time_limit_s": 300,
  "mip_rel_gap": 0.0,
  "num_workers": 8,
  "heuristic": {"enabled": true, "refine_rounds": 3}
}
```

## 9.2 `backend`

- `"scipy"`：`scipy.optimize.milp`，默认；
- `"highspy"`：Highs Python API，可选。

两个后端使用同一个建模层，切换时不需要改模型。

## 9.3 `time_limit_s`

每个格点阶段 1 和每个 ε 点阶段 2 的求解时间上限（秒）。

## 9.4 `mip_rel_gap`

MILP 相对 gap 终止条件：

- `0.0`：追求最优；
- `0.01`：允许 1% 相对 gap。

## 9.5 `num_workers`

格点并行 worker 数：

- `1`：串行，便于调试；
- `>1`：使用 `ProcessPoolExecutor` 并行跑格点阶段 1；
- worker 内求解器仍尽量单线程，保证可复现性。

## 9.6 `heuristic`

贪心初始解模块：

- `enabled`：是否启用；
- `refine_rounds`：块坐标 refinement 轮数；
- 价值：
  - 给出 composite 下界；
  - 给格点排序打分；
  - 作为 MILP 超时 fallback；
  - 作为回归断言：MILP 结果不应差于贪心。

# 10. 输入校验规则

| 编号 | 规则 | 本文档中的物理含义 |
|---|---|---|
| V1 | 边界严格递增，单周期在 `(0,1)`，双周期在 `(0,0.5)`；声明边界数 ≤ 6 | 相位边界合法 |
| V2 | `green_mask` 长度 = 边界数 + 1；必须同时有绿有红；首尾不能同时为绿；派生窗口数 ≤ 3/6 | 绿红区间合法 |
| V3 | 可调范围 `lo ≤ 0 ≤ hi`；`min_phase_s > 0` | 微调与最小相位合法 |
| V4 | 红带 nodes 长度=2；绿带≥2；节点在干线上并按方向排序 | 红波只能相邻对，绿波必须链式 |
| V5 | 带需求节点沿行驶方向连续 | 不能跳路口 |
| V6 | 软约束必须给 `coef` 和 `owner`；硬约束不得有 `soft` | 约束类型清晰 |
| V7 | 全局约束不得引用 `boundary` / `window_duration` / `red_duration` | 有方案归属歧义 |
| V8 | 周期、速度、距离为正；倍率 >0 | 物理量必须为正 |
| V9 | 每个路口至少 1 个方案 | 每路口必须可选 |
| V10 | margin `delta_min_s ≥ 0` 且小于链上最小窗口宽度 | margin 不应明显不可达 |

实现中还额外检查：

- 方案 id 唯一；
- 路口 id 合法；
- 距离至少有一个公共值或分方向值；
- 方案约束中端点索引有效；
- 全局带宽引用的需求存在；
- 全局偏置引用路口存在。

# 11. 数学模型与物理原理

## 11.1 符号表

| 符号 | 含义 | 单位 |
|---|---|---|
| `I` | 路口集合 | — |
| `d` | 方向 `up` / `down` | — |
| `P_i` | 路口 `i` 的可行候选方案 | — |
| `W_{i,p,d}` | 方案 `p` 在方向 `d` 的绿灯窗口 | — |
| `K_{i,p,d}` | 窗口数 | — |
| `B` | 带需求集合 | — |
| `S_b` | 需求 `b` 的有序节点列表 | — |
| `Q_b` | 需求 `b` 的最大带槽数 | — |
| `C` | 公共周期 | 秒 |
| `κ` | 速度倍率 | — |
| `τ_i^d` | 路段行程时间 | 秒 |
| `T_j` | 链上累计行程时间 | 秒 |
| `s̄, ē` | 窗口名义比例起止 | — |
| `x_{i,p}` | 方案选择 | 0/1 |
| `φ_i` | 路口偏置 | 秒 |
| `δ` | 端点微调量 | 比例 |
| `z` | `x·δ` 线性化辅助变量 | 比例 |
| `ŝ, ê` | 有效窗口端点秒值 | 秒 |
| `u_{b,q}` | 带槽起点 | 秒 |
| `β_{b,q}` | 带槽宽度 | 秒 |
| `e_{b,q}` | 带槽存在性 | 0/1 |
| `a_{b,q,j,k}` | 绿带窗口槽指派 | 0/1 |
| `n_{b,q,j}` | 绿带回绕周期数 | 整数 |
| `ag_{b,q,g}` | 红带上游绿窗槽指派 | 0/1 |
| `ar_{b,q,r,k}` | 红带下游红窗实例指派；`k` 为下游周期偏移 | 0/1 |
| `σ` | 软约束/margin 违反量 | 秒 |

## 11.2 格点常量化

对每个 `(C, κ)`：

```text
τ_i^up   = distance_up_i / (κ · speed_up_i)
τ_i^down = distance_down_i / (κ · speed_down_i)
```

链上的累计时间：

```text
T_1 = 0
T_j = T_{j-1} + τ_{j-1}^{d_b}
```

## 11.3 派生窗口重构（v2）

每个路口方向维护最多 `K_i^max` 个派生绿窗槽位：

```text
K_i^max = max_p K_{i,p,d}
```

预处理为每个方案预计算「窗口槽位 k → 起点 edge a、终点 edge b、wrap」。

```text
value(edge) = 0 / 1（周期边）
            或 (pos_r + offset + δ)（声明边界，双周期复制带 +0.5 offset）
ŝ_{i,d,k} = Σ_p x_p · value_p(a_p)
ê_{i,d,k} = Σ_p x_p · (value_p(b_p) + wrap_p · C)
h_{i,d,k} = Σ_p A_{i,p,d,k} · x_p
```

其中 `A=1` 表示方案 p 至少有 k 个派生绿窗。`z = x·δ` 用 McCormick 线性化：

```text
z ≤ hi·x        z ≥ lo·x
z ≤ δ − lo·(1−x)   z ≥ δ − hi·(1−x)
```

- 单方案路口把 `x=1` 代入，不建 z；
- 双周期复制边界复用同一个 δ；
- 红窗仍由绿窗补集生成（gap + wrap）；
- C4–C13 的公式形式不变。

## 11.4 C1：方案选择

```text
Σ_p x_{i,p} = 1        ∀i
```

每个路口恰好选择一个方案。

## 11.5 C2：方案内硬约束

对方案 `p` 的每条硬约束：

```text
expr ≤ rhs + M · (1 − x_{i,p})
expr ≥ rhs − M · (1 − x_{i,p})
```

相等约束拆成两个方向。

仅选中方案时生效。

## 11.6 C3：方案内软约束

```text
expr ≤ rhs + σ_c + M · (1 − x_{i,p})
expr ≥ rhs − σ_c − M · (1 − x_{i,p})
σ_c ≥ 0
```

违反量乘 `coef` 进入：

- `intersection_loss`（路口损失）；或
- `composite`。

## 11.7 C4：绿带窗口指派

```text
Σ_k a_{b,q,j,k} = e_{b,q}          ∀b,q,j
a_{b,q,j,k} ≤ h_{n_j,d_b,k}
```

含义：

- 带槽存在时，链上每个节点必须恰好选择一个窗口槽；
- 槽位必须被选中方案提供。

## 11.8 C5：绿带包含约束

```text
u_{b,q} + T_j ≥ φ_{n_j} + ŝ_{n_j,d,k} + n_{b,q,j} · C − M(1−a)
u_{b,q} + T_j + β_{b,q} ≤ φ_{n_j} + ê_{n_j,d,k} + n_{b,q,j} · C + M(1−a)
```

物理意义：

- 带在节点 `j` 的到达时间为 `u + T_j`；
- 该时间必须落在所选绿灯窗口内；
- 方向、周期回绕通过整数 `n` 对齐。

带宽不需要显式 min：

- 上述不等式天然让 `β` 被链上最紧窗口卡住；
- 最大化目标会自动把 `β` 顶到最紧处。

## 11.9 C6：绿带存在性

```text
β_{b,q} ≤ C · e_{b,q}
```

- `e=0` 时带宽为 0；
- 带不存在时不缩小可行域。

## 11.10 C7：多带排序与窗口独占

排序：

```text
u_{b,q} ≤ u_{b,q+1}
```

窗口独占（默认）：

```text
Σ_q a_{b,q,j,k} ≤ 1
```

含义：同一需求的两条带不能在同一路口的同一窗口槽位共存。

`allow_window_sharing=true` 时改为条件不重叠约束。

## 11.11 C8：绿带 margin 短缺

```text
σ_left  ≥ δ_min − (u + T_j − φ_j − ŝ − nC)  − M(1−a)
σ_right ≥ δ_min − (φ_j + ê + nC − u − T_j − β) − M(1−a)
```

物理意义：

- 左 margin：带到窗口左端点的距离；
- 右 margin：窗口右端点到带终点的距离；
- 不足 `δ_min` 的部分按 `coef` 罚款。

## 11.12 C9：红波带构造

红波带只能存在于相邻两个路口。

> 实现说明：C9 采用因式分解形式。红带指派拆成 `ag`（上游绿窗槽）和 `ar`（下游红窗实例，含周期偏移 `k`）两组独立二进制，通过共享的 `u、β` 耦合；实例独占改为时间分离约束，并用 C13 有效不等式和 k 预剪枝压缩搜索空间。

下游红窗由有效绿窗补集生成：

```text
gap_r:  [ê_r, ŝ_{r+1}]
wrap_r: [ê_r, ŝ_1 + C]
```

`wrap` 段显式生成，用于跨 0/C 红波。

红带指派：

```text
ag_{b,q,g} = 1       带槽 q 使用上游绿窗槽 g
ar_{b,q,r,k} = 1     带槽 q 使用下游红窗实例 (r,k)
Σ_g ag_{b,q,g} = e_{b,q}
Σ_{r,k} ar_{b,q,r,k} = e_{b,q}
```

其中：

- `g`：上游绿窗槽；
- `r`：下游红窗槽；
- `k`：下游红窗周期偏移（不再需要独立的上游偏移）。

包含约束：

```text
u_{b,q}         ≥ φ_i + ŝ_{i,d,g} + τ_{i→j} − M·(1 − ag)
u_{b,q} + β     ≤ φ_i + ê_{i,d,g} + τ_{i→j} + M·(1 − ag)
u_{b,q}         ≥ φ_j + red_start_r + kC − M·(1 − ar)
u_{b,q} + β     ≤ φ_j + red_end_r   + kC + M·(1 − ar)
```

物理意义：

- 上游绿窗平移 `τ` 后与下游红窗求交；
- 交集宽度就是红波带宽；
- `k` 处理下游红窗周期副本和跨 0 情况。

`k` 预剪枝：

```text
( ŝ_g + τ − re_r − kC,  ê_g + τ − rs_r − kC ) ∩ (−C, C) ≠ ∅
```

满足上式才可能重叠；建模前用端点上下界计算，并只保留至少与某个对方槽位兼容的 `ag` 或 `ar`。

时间分离（任意两条存在的带不重叠）：

```text
u_{b,q} + β_{b,q} ≤ u_{b,q2} + M·(2 − e_{b,q} − e_{b,q2})    ∀ q < q2
```

C13 带宽有效不等式：

```text
β_{b,q} ≤ Σ_g W_g · ag_{b,q,g} + C·(1 − e_{b,q})
β_{b,q} ≤ Σ_{r,k} Wr_{r,k} · ar_{b,q,r,k} + C·(1 − e_{b,q})
β_{b,q} ≤ C · e_{b,q}
```

## 11.13 C10：用户全局约束

硬约束：

```text
expr ≤ rhs
expr ≥ rhs
expr = rhs
```

软约束：

```text
expr ≤ rhs + σ
expr ≥ rhs − σ
```

违反量按 `owner` 归属 composite 或 intersection_loss。

## 11.14 C11：双周期一致性

对复制窗口的每个可调端点：

```text
δ_copy = δ_orig
```

否则求解器会让两个半周期不对称，等价于偷变成全周期方案。

## 11.15 目标函数

```text
composite = Σ_b weight_b · Σ_q β_{b,q}
          − Σ_{green, margin} coef_m · (σ_left + σ_right)
          − Σ_{soft, owner=composite} coef_c · σ_c

L = Σ_{soft, owner=intersection_loss} coef_c · σ_c
```

单位统一为秒。

## 11.16 两阶段求解

阶段 1：

```text
max composite
s.t. C1–C13
```

记录每个格点的：

```text
B*(C, κ)
```

阶段 2：

对 top-k 格点：

```text
for l = 0 .. num_points:
    ε_l = (l / num_points) × relax_max × |B*|
    min L
    s.t. composite ≥ B* − ε_l
         其他约束不变
```

`l = 0` 必须求解，用于找到在 composite 最优前提下的最低损失解。

## 11.17 big-M

每个约束类型使用紧的 M：

- 包含约束：约 `T_max + 2C`；
- 方案激活/软约束：按约束两端最大可能差；
- 禁止使用 `1e6` 量级的通用大 M。

# 12. 求解流程

完整流水线：

```text
输入校验 V1–V10
      │
      ▼
逐格点并行：
  ① 预处理过滤方案可行性
  ② 贪心初始解
  ③ 构建 MILP
  ④ 阶段 1：max composite
      │
      ▼
汇总所有 B*，排序
      │
      ▼
阶段 2：top-k 格点 ε-constraint 扫描
      │
      ▼
输出 JSON + 时距图 + Pareto 图
```

## 12.1 预处理层

对每个 `(i, p, C)`：

- 固定窗口方案：纯算术代入硬约束；
- 可调端点方案：解一个微 LP：
  - 变量：δ；
  - 约束：硬约束、窗口有序、不重叠、V1、双周期一致性；
  - 不可行则剔除方案并记录诊断；
- 某路口全部方案不可行 → 格点不可行，跳过。

## 12.2 贪心初始解

步骤：

1. 每个路口选择路口损失最小的可行方案；
2. 基于锚点带起点，逐路口枚举候选偏置；
3. 构造链式带/红波重叠，精确计算带宽；
4. 块坐标 refinement。

价值：

- composite 下界；
- 格点排序；
- fallback；
- 回归对照。

## 12.3 阶段 1

每个格点独立构建 MILP：

- 最大化 composite；
- 记录状态、B*、gap、耗时；
- 并行进程池，worker 内单线程求解。

## 12.4 阶段 2

对 top-k 格点：

- `min L`；
- 追加 `composite ≥ B* − ε_l`；
- 每个 ε 点输出完整方案。

## 12.5 不可行诊断

如果 MILP 返回 infeasible：

- 对所有约束按组加松弛变量；
- 最小化总松弛；
- 定位使模型恢复可行的约束组；
- 输出诊断报告。

# 13. 解的结构与物理含义

## 13.1 格点结果 `grid_results`

```json
{
  "cycle_s": 90,
  "speed_ratio": 1.0,
  "status": "optimal",
  "composite_best": 42.5,
  "heuristic_bound": 38.0,
  "solve_time_s": 12.3,
  "dropped_plans": [
    {"intersection": "I3", "plan": "I3_P2", "reason": "min_green 15s violated (12.0s)"}
  ],
  "message": ""
}
```

物理含义：

- `cycle_s`：公共周期；
- `speed_ratio`：速度倍率；
- `composite_best`：阶段 1 最优 composite；
- `heuristic_bound`：贪心下界；
- `dropped_plans`：在该周期下被预处理剔除的方案；
- `status`：`optimal` / `feasible` / `time_limit` / `infeasible` / `error` / `skipped_infeasible`。

## 13.2 Pareto 点

```json
{
  "epsilon": 0.0,
  "composite_actual": 42.5,
  "intersection_loss": 18.0,
  "solution": { ... }
}
```

含义：

- `epsilon`：放宽量；
- `composite_actual`：用解向量重算的实际 composite；
- `intersection_loss`：路口损失；
- `solution`：完整方案。

## 13.3 `solution`

```json
{
  "plan_selection": {"I1": "I1_P2", "I2": "I2_P1"},
  "offsets_s": {"I1": 0.0, "I2": 33.5},
  "adjustments": {"I2_P1.up.0.end": 0.03},
  "bands": [
    {"demand": "GW_up_full", "slot": 1, "exists": true,
     "width_s": 21.0, "start_at_anchor_s": 5.0,
     "windows": {"I1": 1, "I2": 2},
     "red_instance": null}
  ],
  "constraint_violations": [
    {"id": "c7", "violation_s": 3.0, "cost": 15.0, "owner": "composite"}
  ]
}
```

- `plan_selection`：每个路口选中的方案；
- `offsets_s`：路口周期起始偏置，秒；
- `adjustments`：端点微调量，周期比例；
- `bands`：每条带的存在性、宽度、起点、所用窗口；
- `constraint_violations`：软约束违反记录。

# 14. 时距图与 Pareto 图读法

## 14.1 时距图

坐标：

```text
横轴 = 时间 Time (s)
纵轴 = 沿干线累计距离 Distance (m)，向上递增
```

绘制规则：

- 每个路口中心线上、下各一条灯条：
  - 上：上行；
  - 下：下行；
- 灯条中：
  - 绿色 = 上行绿灯窗口；
  - 湖蓝色 = 下行绿灯窗口；
  - 红色 = 红灯时段；
- 绿波带：
  - 上行带：左下 → 右上；
  - 下行带：左上 → 右下；
  - 绘制在对应方向灯条中心线上；
- 红波带：
  - 相邻路口间的红色斜向重叠区；
- 灯条和带都按周期重复，铺满可见时间范围。

## 14.2 Pareto 图

- 横轴：composite band objective / C，越大越好；
- 纵轴：intersection loss / C，越小越好；
- 两个目标都除以周期 C，变成无量纲值，可跨周期比较；
- 只绘制非支配点；
- 点标注 `P1, P2, ...` 和对应 `ε`；
- 越靠右下越好：高带宽、低路口损失。

## 14.3 格点热力图

当周期 `C` 和速度倍率 `κ` 有多档候选时，可以绘制 2×2 热力图：

- 第 1 格：`bandwidth_objective_ratio = bandwidth_objective_s / C`，越大越好；
- 第 2 格：`negative_margin_loss_ratio = −margin_loss_s / C`，越接近 0 越好；
- 第 3 格：`negative_intersection_loss_ratio = −intersection_loss_s / C`，越接近 0 越好；
- 第 4 格：留空，供以后扩展。

每格横轴为速度倍率，纵轴为周期。色阶为淡绿（好）→ 白色（中等）→ 淡红（不好），
并按每个指标自身的实际最小/最大值自适应。

生成脚本：

```bash
python examples/plot_grid_heatmaps.py
```

输出：`examples/diagrams/09_grid_heatmaps.png`。

# 17. 调试与常见错误

## 17.1 校验失败

先看 `GWValidationError`：

- 错误信息会带 `V` 编号；
- 重点检查单位、节点顺序、红带长度、`green_mask` 首尾规则、全局约束是否引用 `boundary`。

## 17.2 格点不可行

可能原因：

1. 某方案在 `C` 下违反最小绿；
2. 可调端点无法同时满足硬约束和窗口有序；
3. 某路口全部方案不可行。

处理：

- 查看 `dropped_plans`；
- 放宽方案可调范围；
- 增加候选方案；
- 检查 min green 等硬约束是否随周期变化。

## 17.3 模型不可行

可能原因：

1. 用户跨路口硬约束冲突；
2. 带宽硬约束不可满足；
3. 建模 bug。

系统会自动跑 `InfeasibilityDiagnoser`，返回使模型恢复可行的约束组。

## 17.4 图里带穿红灯

优先检查：

- 优化模型是否可行；
- 绘图层是否正确使用路口偏置 `φ`；
- 绿波带是否按方向绘制在对应灯条中心线上；
- 红波带是否使用了正确的上游/下游周期偏移。

当前实现已经对这些点做过几何检查。

## 17.5 数值容差

MILP 有微小数值容差：

- 带宽、绿窗边界可能出现 `1e-6` 秒级偏差；
- 判断“穿红”时应使用合理容差，例如 `1e-3 s`。

## 17.6 单位陷阱

- `boundaries[].pos_r` / `adjust` 是周期比例，不是秒；
- `rhs_ratio` 是比例，`rhs_s` / `rhs` 是秒；
- `green_mask` 是布尔数组；
- `offsets_s`、`bandwidth`、`margin` 是秒；
- `distance_*` 是米，`speed_*` 是米/秒。
